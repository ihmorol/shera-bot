## What OpenMausBot is (verified reading)

An open-source "Grok Bot alternative": a local-first chat app where each sidebar contact is a real agent — Claude or Codex CLI processes running under the hood — with its own personality, model, cloud computer, and connected apps, with approval gates ("Talk to them like contacts. ## Decision and rationale

**1. The owner's option A — build Shera Bot on top of OpenMausBot — is REJECTED, on the recorded E15 alternative-(a) grounds, with the mismatches now concrete:**

- **Product-shape mismatch.** OpenMausBot is a single-user, local-first DESKTOP product whose bots are locally supervised CLI processes. Shera Bot is a server-side web product: the runtime gateway owns authoritative transitions, persistence, event sequencing, approvals, leases, supervision, and recovery (D11); central PostgreSQL owns control-plane records; container-local SQLite owns product state; five-account tenancy (AC1); Pack → Operations → Agents contracts (G1) with typed task-run creation (G2).
- **Stack mismatch.** Electron + local process supervision + croner timers versus the PRD §17 TypeScript monorepo whose scheduling is the runtime-owned ledger over cron-parser/chokidar that E37 already shipped. Adopting OpenMausBot's scheduling would create a SECOND occurrence-math truth, exactly what the E37 S28 record forbids.
- **Sunk and governing work.** Main at `a58311a` carries 26 merged slices (S01–S27 including the S24 credit ledger and the S31 checkpoint/recovery machinery with its v21 migration chain), with S28 (PR #71) and S32 (PR #72) pushed to WIP awaiting their before-merge loops. A rebase would submerge the runtime gateway — "the actual product" per E15's rationale — and discard all of it.
- **Upstream volatility.** Pushed daily (last 2026-11-05); 6,867 files. A vendored base is perpetual merge debt against G8's per-merge owner approval.

**2. The owner's option B — use its code, structure, and information to build faster — is ADOPTED under the E15 tiers, scoped to the slices that remain:**

- **Tier classification.** The Apache-2.0 core is Embed-eligible (on the S01 allowlist: MIT / Apache-2.0 / BSD / ISC). `enterprise/` is NEVER embedded or pattern-copied into runtime code — treated like the E15 AGPL tier (docs-only reading). Any embedded file carries its upstream notice per Apache-2.0 §4, and `NOTICE`'s T3 Code attributions travel with any file that descends from them.
- **S35 Deployment (issue #36) — structural reference, strong.** `deploy/docker-compose.yml` is the same shape S35 must ship: one-tenant Compose + Caddy for TLS/login (Caddy in the server's network namespace, the server never binding a public interface), `.env.example`-driven configuration, healthcheck, `restart: unless-stopped`, init/shm sizing for bundled browsers, and the prebuilt-image-or-build-from-source posture. `deploy/local/README.md` + `deploy/local/{Dockerfile,Caddyfile,.dockerignore}` and `deploy/podman/` give the runbook variants; `.github/workflows/shared-terminal-smoke.yml` is the smoke-test workflow pattern; the boot response `{"edition":"oss"}` pattern is the monitoring-shape reference. This mirrors E15's S35 embeds (Docker Compose; Caddy) with a working, permissively-licensed example — read it before designing, per the E15 anti-creativity rule.
- **S34 Acceptance ledger and criteria runner (issue #35) — architectural pattern, strong.** `evals/` implements "evaluate the harness, never the models": a three-tier offline harness — tier 1 deterministic scripted scenarios (pure-data JSON fixture files), tier 2 redacted golden-thread replay against COMMITTED TRACE BASELINES, tier 3 opt-in live-model smoke behind an explicit env flag (structurally the G7 posture) — with hermetic runs, scorers as pure functions over frozen snapshots that never touch a server, and JSON+markdown per-run reports.
