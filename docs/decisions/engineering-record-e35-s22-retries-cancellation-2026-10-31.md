## Decision and rationale

**The retry policy is runtime-owned data, and the attempt ledger is the journal.** `retry-policy.ts` is a pure classification table + bounded decision: typed failure codes map to `transient` / `permanent` / `ambiguous` (unknown codes classify as ambiguous — fail-closed, the E13 needs_human default at the retry layer; the lookup normalizes case because worker `failure_class` strings arrive from child processes as free bounded text), and `decideRetry` maps transient → retry (attempt n, bounded backoff 1s/2s/4s from a fixed schedule — no unbounded exponential, no jitter, deterministic tests), permanent → immediate typed failure (AC2), ambiguous → pause-for-review with the reason recorded (AC10/E13). The bound is policy data with no agent-suppliable input (G2: nothing an Agent proposes widens it). The RetryCoordinator applies each decision to a run row through the shared row-lifecycle applier (below) and owns the backoff CLOCK through an injected `schedule` seam (the runtime owns its own timers — BullMQ/Redis remains rejected per E27); the ATTEMPT LEDGER is the journal itself — consumed retries are the max `attempt` across the run's `task.retry_scheduled` envelopes on `task:<run_id>`, so a fresh coordinator (or a restarted gateway) reads the same truth the UI renders (AC3), and every decision journals a `run.failure_decided` audit record (what failed, what was decided, why) in the same transaction as the lifecycle envelope.

**One transition applier, never a second state machine.** `run-lifecycle.ts` applies a D8 transition to a ROW-based run (an OperationRun row has no journal-rebuildable TaskRun projection, so the approvals path's rebuild discipline does not apply): legality is checked against the SAME `TASK_TRANSITIONS` table the pure transition function serves (table as data, D23 rule 5), including the actor vocabulary and the retry attempt bound; the optimistic version is 1 + the journalled lifecycle count on the run's stream, baked into a DETERMINISTIC event id (`evt_cmd_<command>_<run>_v<version>`) so a lost concurrent race deduplicates at the journal append (the winner's row is the contract — the same idempotency shape as the collaboration appends); the contract lifecycle envelope (`buildTaskTransitionEvent`, the same builder the approvals path journals through) plus the audit record commit in ONE transaction (D10); the row write goes through the run-control seam AFTER the evidence commits (journal-first, the E27 aftermath ordering — a seam-write failure is contained, never rolled into silence), which is what makes the composed `RunFlowOperationsService` start/stop workers from the committed state.

**The supervisor consults the policy for worker-REPORTED failures only.** S16/E27's escalation is unchanged — crash exits, hangs, protocol violations, and handshake timeouts still land RECOVERY_REQUIRED (the recovery slice's territory). A worker-REPORTED error frame (`failure_class`) is a classified failure: the supervisor's escalation runs to completion (process reaped, `worker.crashed` committed as the aftermath-completion marker) and then hands (workspace, run, worker, failure class, crash event id) to the injected `onWorkerReportedFailure` seam — the composed RetryCoordinator — whose decision owns the run state; unwired or throwing handlers fall back to the recovery write (a failure is never silently dropped, G5). The composition wires this seam; without a worker harness the coordinator still exists (the policy is a runtime concern, not a harness concern) and behavior is exactly pre-S22 (G4).

**Cancellation walks the recorded D8 two-step and tears down every holding.** `RunCancellationService.cancelRun` (user/admin actor — an agent actor is a typed refusal): `cancel_task` → CANCELLING (journalled, row advanced — the composed flow's stop hook fires from the row write), then the TEARDOWN (each step idempotent and contained): pending retry timers dropped, in-flight/withheld tool executions cancelled through the S21 executor seam (`ToolExecutor.cancelForTask` — withheld gated executions are dropped so the effect can NEVER run post-cancel, and non-terminal history rows sweep to `cancelled`; terminal rows keep their outcome), the worker stop awaited through the supervisor port (the process-group kill), non-terminal child runs cancelled in turn (the originating actor's action ripples; terminal children are never resurrected; the E1 dequeue already drops terminal runs, so queued children never start — AC5), write leases force-released through `releaseLeasesForTask` (D6/S17: a lease never outlives its task), the S24 credit-reservation seam fired (see the seam note below), pending approvals resolved CANCELLED via `ApprovalsService.cancelPendingForTask` (never rejected — the five choices are distinct vocabulary; no grant path exists on that method by construction, AC9/D9), then `cancel_complete` → CANCELLED with the preserved inventory in the answer: the run's artifact ids and its journal event count — logs and partial outputs are listed AND intact (AC6; cancel deletes nothing).

**Deterministic outcomes on races and replays (AC7).** A CANCELLED run answers `already_cancelled` (a second cancel is a typed no-op, never an error); a run that settled first answers `already_settled` with its terminal state (the cancel lost the race deterministically; nothing corrupts — the version-guarded transitions give the guarantee); a CANCELLING run re-runs the convergent teardown (every step idempotent) so a crashed first attempt cannot wedge the run. All outcomes are typed 200s on the HTTP surface; `not_found` is the one 404.

**Process-tree termination is the recorded S19 pattern, generalized (AC15, D27/D32).** The production worker spawn adapter now spawns the worker in its OWN process group (`detached` on POSIX — prlimit execs the worker, so the worker IS the group leader), every kill goes to the whole group (negative-pid, with the direct kill as fallback), and `waitForExit` resolves only after the GROUP has been reaped (a bounded post-exit probe: while any group member is alive, SIGKILL the group) — a worker that exits gracefully on the shutdown frame must not orphan its descendants, the exact S19 validation-runner lesson. The chunk-1 escalation order (shutdown frame → SIGTERM → SIGKILL) is unchanged. The composition test spawns a real descendant (`sleep`) and asserts with a real `kill(pid, 0)` probe that nothing survives the cancel.

**The S24 credit-reservation seam is honest, not fabricated.** The cancellation path calls an optional `reservations.releaseForRun(workspaceId, runId)` port; the composition wires a recorder that journals a redacted `credit_reservation_release_requested` fault event marked `s24-credit-ledger-not-built`. The credit ledger is slice S24 — no fake ledger, no fake balance (G4); the port is the seam S24's ledger implements, and the call is visible evidence.

**The browser surface is allowlisted and session-bound.** The contracts trust boundary adds exactly two paths: GET `/v1/operations/:op/runs/:run/events` (AC3's read) and POST `/v1/operations/:op/runs/:run/cancel` (AC15's command) — exact shapes, nothing else in the run segment opens (pinned by the contract boundary test). The cancel joins the proxy's SESSION_ACTOR_BINDINGS: `cancelled_by` is rebuilt from the authenticated session server-side (the S20 decision convention) — the browser never asserts an identity.

**UI (§S3/S4 stop control, S11 run states).** The runs panel gains the per-run stop control on every ACTIVE D8 state, with an INLINE confirmation (not a modal — the decision is small, scoped to one card, and what it protects is named in place) that names exactly what stops — the worker process tree, in-flight tool work, and any queued child runs (with the count) — and what survives: logs and partial outputs. Focus lands on the confirming action; Escape or "Keep running" returns without acting; the confirmation closes itself the moment the run settles (a taste-pass finding: the first build left the stale dialog open under its own answer). RETRYING renders the TRUE attempt count from the run's journal (`data-attempt` from the `task.retry_scheduled` envelopes; a failed read renders NO number — never a guess), CANCELLING is the honest busy state (aria-busy, no second stop control), and CANCELLED reads "Stopped — logs and partial outputs are kept." — stopped copy in the muted vocabulary, never failure styling. The AC3 grep leg is a permanent web test that scans components and libs for hardcoded attempt totals — it caught one REAL instance of the recorded fixture-truthfulness defect class (`cards.tsx` rendered "retries: N of 3"); the card now renders the count alone ("retries used: N") and the fixture comment was reworded.

## Scope corrections and recorded deviations

- **BullMQ/Redis (the issue's leverage note) — REJECTED, per E27.** The recorded S16 decision rejected Redis for the prototype (the runtime owns its own clocks and queues); the retry policy rides the runtime's own injected scheduler seam with the journal as the durable ledger. The Temporal RetryPolicy semantics remain the pattern reference only: bounded attempts (3), bounded backoff, then pause-and-notify — implemented as recorded in PRD §8, not as an embedded dependency. No new dependency was adopted in this slice.
- **"Notifies" on retry exhaustion:** the pause's notify surface in this slice is the durable `task.paused` envelope (reason `retry_exhausted`) plus the post-commit live fanout path; the notification center is S30's. Recorded here, not silent.
- **Executor in-flight cancellation scope:** the in-process binding family is synchronous, so today's reachable cancellation surface is the withheld executions (dropped — the effect never runs post-cancel) and the non-terminal row sweep. The AbortController registry rides `ctx.signal` for the process-backed family (S26's escalation hook), recorded in E33's own seam note.
- **UI gate ran against the PRODUCTION web build (`next build` + `next start`).** In dev mode (Turbopack, Next 16.3.5) the container gate never resolved in this stack — the app's own hydration-time fetches hung while identical in-page probes returned 200 (recorded in the capture harness's history); the prod build resolves instantly. The committed captures are prod-build captures; the harness keeps the dev path for future diagnosis.
- **Worker-error retry entry point:** the coordinator's production callers today are the supervisor's worker-error seam and the service-level tool-failure entry (`handleToolExecutionFailed` shape = the same `handleRunFailure`); real tool-execution failures inside row-based runs arrive with S25/S26's tool families through the same entry.

## Alternatives considered (preserved)

- **Journal-rebuildable TaskRun projections for row runs (the approvals path's rebuild):** rejected — a row run has no `task.created` envelope, and inventing one (a synthetic trigger/pack pin) would be fabricated projection data (G4). The shared applier validates against the same transition TABLE and journals the same envelopes; the rebuild path stays exactly where the journal actually holds the creation record.
- **Retry decisions inside the supervisor:** rejected — the supervisor owns supervision, not policy; the injected decision seam keeps one decision point and the E27 recovery posture for unclassified causes verbatim.
- **Cancelling children by direct row write (the S20 cascade shape):** rejected for S22 — a child with a live worker would orphan it, because repository writes bypass the run-flow hooks. The cascade re-enters the full cancellation path (two-step D8 per child, awaited worker stop), bounded at depth 5.
- **Immediate group SIGTERM at t=0 (skipping the shutdown frame grace):** rejected — E27 recorded the escalation order; the post-exit group reap closes the orphan window without reordering anything.
- **A modal for the stop confirmation:** rejected — the craft floor's "exhaust inline alternatives first"; the decision is scoped to one card and the naming copy lives where the decision is made.
- **`pause_retry_exhausted` from FAILED / a RETRYING→FAILED row:** rejected — the D8 table has no such rows on purpose; a permanent failure during a retry attempt rides retry_attempt (RETRYING→RUNNING) then fail_task (RUNNING→FAILED), which is also the truthful narrative (the attempt started, then failed).
