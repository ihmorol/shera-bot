## Decision and rationale

**The supervision shape: ONE worker process per run, governed by the TASK STATE, not a chat timer.** `TaskWorkerSupervisor` (`apps/user-runtime/src/modules/workers/task-worker-supervisor.service.ts`) is the task-state sibling of the S12 `SessionSupervisor`: a worker spawns ON DEMAND when a run needs it — nothing spawns at construction or boot — and a healthy worker runs until done or stopped. There is no idle hibernation and no warm-reuse policy for workers (AC25: browser closure and session hibernation never stop the run's worker). The one-LIVE-worker-per-run rule is enforced in-process by coalescing concurrent `startWorker` calls; successive incarnations across a run's life each get their own `worker_id` row under the durable key `(workspace_id, run_id, worker_id)` (v8 `task_workers` migration — E12-scoped, the v4/v5/v6 no-FK discipline, state vocabulary `starting|running|stalled|exited|killed`). The AC25 independence is pinned by a test composing a `SessionSupervisor` and this supervisor over the SAME journal and proving the Agent's session hibernates while the run's worker continues to completion.

**Crash lands the run in RECOVERY_REQUIRED, never FAILED — the choice, stated.** A worker-reported error frame, a protocol violation, a crash exit, a handshake timeout, and a watchdog stall all escalate (shutdown frame → SIGTERM → SIGKILL, the S12 discipline) and leave TWO durable traces: a `worker.crashed` journal event on the run's stream and the run moved through the seam to `RECOVERY_REQUIRED` (D8). FAILED was rejected deliberately: it is TERMINAL in the D8 vocabulary, and recording a crash as terminal would foreclose the D32 recovery policy ("worker crash with safe checkpoint → restart and resume") at the state machine level. Which crashed runs actually resume — and which are proven unsafe to resume and only then failed — is the recovery slice's decision (D32/D33/E13); this slice records the evidence and stops. Supporting discipline: the crash event journals only once the escalation completed (the aftermath-COMPLETION marker — when the event is visible, the row is terminal and the process reaped); the run-state write follows the crash evidence and is GUARDED (a terminal run is never resurrected); a failure in either unit is contained to a fault log, and the gap class that leaves is exactly what chunk-3's boot reconciliation closes (below).

**The queue is lease rows + the in-process supervisor — BullMQ/Redis was rejected.** E1 could have been built on a Redis-backed queue (BullMQ), and that was rejected on the records: D10 makes the container-local SQLite the authority for this runtime's product state, and PRD §17 pins Redis as "transient queues, pub/sub, and live-event fanout only — never the source of truth." An admission queue whose pending-work state and lease truth lived in Redis would make Redis a SECOND state store and add a network dependency to a single-VM runtime whose whole D10 posture exists to avoid exactly that. Instead the queue is durable SQLite state the runtime already owns: a refusal marks the run QUEUED on the run row (through the D8-validated seam) with a `worker.queued` journal event, and live-worker truth is the `task_workers` rows (inserted before spawn, finalized on exit). Restart survival falls out of the same store — no replay bridge between two systems to design.

**Kernel enforcement via prlimit(1): the gate SCHEDULES, the kernel ENFORCES.** `maxWorkerMemoryBytes` is not merely counted — it is also handed to the spawn request as a REAL kernel limit: the worker command is wrapped `prlimit --as=<bytes> --nproc=<count> -- <file> <args…>` (`worker-process-spawn.ts`), exec'd as a BINARY — never through a shell, so there is no argv-injection surface and the argv elements reach execve verbatim. `--as` caps per-worker address space (allocation fails inside the child instead of the runtime growing unbounded — proven by the hoarding-worker test: allocation denial → crash recorded → run RECOVERY_REQUIRED); `--nproc` caps per-worker process creation. Honest note on `--nproc`, empirically verified during the slice: RLIMIT_NPROC is enforced per REAL user id, so `--nproc=1` does not merely forbid the child's own forks — it aborts Node at boot because the runtime's boot-time thread creation already exceeds a limit of one for the uid. The pinned test (`--nproc=1`, a fork-happy worker) shows the child dying before ready with the crash recorded — the kernel boundary is the enforcement either way, and the composition default (`maxWorkerProcesses: 4096`) is chosen so a node-based worker child actually boots on an ordinary dev box. A missing prlimit binary is a typed STARTUP failure (`PrlimitUnavailableError` naming the searched paths) resolved once at composition — never a silent fall-back to unlimited workers; a worker spawned with no admission policy spawns unwrapped and must not demand the binary.

**The disk probe fails OPEN, and that posture is documented — not silent.** The `minFreeDiskBytes` floor is measured with a `statfsSync` probe on the runtime data dir before admitting. A failed probe is treated as an OBSERVABILITY GAP, not as pressure evidence: the check is skipped rather than blocking all work on an unmeasurable disk, the posture is written at the site and here, and the probe value surfaces verbatim on the machine-readable pressure read model. The fail-CLOSED direction is kept honest the other way: a policy that DEMANDS a disk floor while providing no dataDir or probe to measure it is a typed startup failure (`AdmissionPolicyError`), never a silently skipped check. The default floor is 0 (no disk gate by default).

**Admission refusal NEVER kills: durable QUEUED with machine-readable reasons, oldest-first dequeue.** The gate answers one question — may another worker start now — and only refuses NEW work: reaching a limit never touches running workers, their leases, or their children (pinned by a dedicated never-kill test). The four machine-readable refusal codes are `worker_limit_reached`, `memory_limit`, `disk_pressure`, `provider_concurrency`, each carrying `{code, limit, current}` plus the gate's own fixed human text (G3 — safe copy, never a harness surface); the reason travels on the durable `worker.queued` event and the run-row state, so the "who is waiting and why" survives restart and replay. Queued runs re-admit OLDEST-FIRST on capacity-free events (worker exit, done, stop) plus the periodic tick as the re-check loop for pressure that clears without an exit (disk space); the dequeue awaits each re-admitted start before considering the next entry so the gate's live-row count is exact between admissions, passes the ORIGINAL spec back (resource limits + provider snapshot), and drops runs that turned terminal (never resurrected). `startWorker` resolves a QUEUED result immediately; coalesced callers receive the same answer rather than retry-looping against a full gate.

**Progress and checkpoints are durable at every frame (D10).** Every progress frame commits its `worker.progress` journal event AND the row's `last_progress_json` in ONE transaction; checkpoints commit `worker.checkpoint` with the opaque D33 payload persisted verbatim; heartbeats renew `lease_expires_at` on the row. Nothing a worker reports lives only in process memory — the journal + the row are what the recovery slice reads to reconstruct what survived. Liveness is any frame: a worker that streams progress but forgets heartbeats is alive and working, never stalled (stalled ≠ slow, the D32 distinction E25 recorded for sessions, mirrored here); `stalled` is reserved for the missed-heartbeat detection on a silent worker.

**Boot reconciliation closes the gateway-death gap class (chunk 3).** `reconcileTaskWorkersAfterRestart` runs at composition startup and does exactly three narrow things: REAP live rows whose pid is proven gone (`kill(pid, 0)`; EPERM counts as alive — a possibly-alive process belonging to another user is never reaped; the row is marked killed BEFORE the `worker.reaped` event appends, the aftermath-completion discipline); RE-QUEUE runs the durable rows left in QUEUED through the SAME supervisor and gate (a fresh refusal queues durably again; a fresh admission starts a real worker; a QUEUED run that still has a live row is someone's live work and is left alone); and COUNT the RECOVERY_REQUIRED runs — re-driving them is a recovery-policy decision this pass deliberately does not make. Runs in other non-terminal states whose workers died with the gateway keep their runs for the recovery slice; only their rows are reaped (row hygiene). Every unit is contained — a failed write or append is fault-logged and the pass continues; a reconciliation gap is an honest fault record, never a crashed boot.

**Run wiring: the D8 transition drives the lifecycle, through ONE state machine.** The composed OperationsService's `applyRunState` additionally drives the supervisor (chunk-3 `task-run-flow.ts`): RUNNING starts the run's worker fire-and-forget (the transition never waits on a spawn — the lifecycle is observable on the run stream); CANCELLING and the terminal states stop it through the chunk-1 escalation (defensively — a run reaching a terminal state by another path never leaves an orphaned worker; stopping without a live worker is a typed idempotent no-op); every OTHER state — RECOVERY_REQUIRED (the recovery slice owns it) and PAUSED (the pause slice) — changes nothing. The supervisor's OWN run-state writes (SUCCEEDED on done, RECOVERY_REQUIRED on crash, QUEUED on refusal) go through the `OperationsRunSeam` holding the SAME service instance — the D8-validated write the runtime gateway owns, with the run's operation resolved from the run row and a cross-workspace run refused typed (E12). No second state machine exists anywhere in the slice. The run-state write commits FIRST; a flow-hook failure is fault-logged — a supervision gap must never fail an already-committed, D8-validated transition.

**Pressure hibernation: the primitive is immediate, journaled, and skips the unsafe — healthy workers are never killed for capacity.** `SessionSupervisor.hibernateIdleSessionsNow("resource_pressure")` (S16 chunk 2) force-runs the SAME graceful idle-hibernation path the natural timer uses, WITHOUT waiting out the idle window, for every ACTIVE session that is safely hibernatable — handshake completed, not already terminating, no in-flight prompt (a registered waiter is never left unsettled; those sessions are skipped, not killed). The given reason is journaled on `session.hibernate` so replay can distinguish a pressure hibernation from the natural idle timer; the method is idempotent. The pinned pressure test shows the posture end-to-end: with capacity full and a run QUEUED, an idle Agent session hibernates NOW while the healthy worker and the queued run simply wait — a worker is NEVER killed to free capacity (PRD §6/E1). Scope honesty: this slice ships the primitive and the machine-readable pressure read model (`supervisor.admissionPressure`: configured, live workers, queued runs, free-disk bytes, limits, per-provider counts); it does NOT wire an automatic trigger that calls the primitive when the gate refuses — which pressure response runs, and when, is a coordination policy left open here rather than silently chosen in composition.

**The G4 harness toggle: absent means byte-identical to before.** `SHERA_WORKER_HARNESS_COMMAND` (one executable path) plus `SHERA_WORKER_HARNESS_ARGS` (whitespace-split, per-spawn placeholders `{run_id}` / `{worker_id}` / `{heartbeat_interval_ms}` substituted at spawn — never a shell) are parsed in the SAME config seam as the session harness knob, with a programmatic override winning. When the knob is absent the worker system is DISABLED: no process ever spawns, the readout reports `configured: false`, and run transitions stay worker-free — pinned by tests (the main-config shape expects `workerHarness: null`; the API suite proves transitions write no rows and no worker events without a harness). The committed fake task worker is the harness command for tests and preview; real worker harnesses arrive with their slices.

**The browser readout is one allowlisted GET — the honest "who is waiting and why".** `GET /v1/workers/admission?workspace_id=…` is the ONE worker surface a browser may read (the proxy allowlist pins it; worker MUTATIONS are refused — the browser renders pressure, never authors it; sibling sub-paths are refused too). The settings surface's Task workers card renders the configured limits, the runtime-wide live count, and THIS workspace's queued runs with their refusal VERBATIM (code + the gate's own text), polling on the shared visible-tab cadence. Honesty rules (G4): `configured: false` renders "not configured" — never a limits table of zeros dressed up as policy; an absent or failed read renders the §2.4 error state. UI_DESIGN S11's "Resource states: queued-on-exhaustion shown as QUEUED with reason (E1: healthy work is never killed for capacity)" now has a real surface (`worker-admission-readout.tsx`) instead of a design line.

## Alternatives considered (preserved)

- **BullMQ/Redis for the admission queue:** rejected — it would make Redis a second state store (admission + lease truth) and add a network dependency the single-VM D10/PRD §17 posture exists to avoid; the durable-row design gives restart survival without a cross-store replay bridge.
- **FAILED on worker crash:** rejected — FAILED is terminal in D8 and would foreclose the D32 recovery policy at the state machine; `RECOVERY_REQUIRED` records the evidence while the recovery slice owns the resume-or-fail decision.
- **cgroups for the kernel limits:** unavailable in this slice — cgroup delegation requires the container runtime, and the runtime has run as a local Node process since E22 (Docker is a standing NOT-verified item); `prlimit`(1) is the per-process kernel mechanism available on the bare VM.
- **Advisory limits only (counting without kernel enforcement):** rejected by the acceptance basis — E1's demand is real limits; the suite proves `--as` denies a memory-hoarding worker at allocation time and `--nproc` denies a fork-happy worker at the kernel boundary.
- **Killing healthy workers (or the oldest worker) to free capacity:** rejected by PRD §6/E1 outright — queue-on-exhaustion without killing healthy work is the product rule the never-kill test pins.
- **A WebSocket fanout for the readout:** rejected for this slice — a low-frequency read needs no second live semantic; the visible-tab poll is honest and removable (the same posture E25 recorded for session presence).
