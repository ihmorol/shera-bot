## Decision and rationale

**The custody boundary is one seam, and it is honest about its prototype form.** Provider credentials live ONLY in the v15 `provider_credentials` table as sealed AES-256-GCM payloads (12-byte random IV + ciphertext + 16-byte GCM tag + key_version columns — no plaintext column exists anywhere in the schema), sealed and opened exclusively by `ProviderCredentialVault` under a container-local 0600 key file beside the database (the D22 "protected bootstrap key" in its prototype form: the container volume is the trust boundary; a deployment-grade secret manager is the production replacement and is exactly why the vault is a composition-wired seam, not a global). `decryptForCall` is the ONLY plaintext-producing path and exists for exactly one caller shape — the adapter assembling one provider request; the plaintext is consumed in-process and never persisted, logged, journalled, or returned. Display answers the store-time masked hint only (at most the final four characters; anything shorter than 12 characters is fully masked), so the ciphertext is never opened for display. Revoke deletes the sealed payload; replace upserts a new one and takes effect on the NEXT call because no plaintext cache exists — no restart, pinned by test. An unreadable or wrong-length EXISTING key file is a typed hard failure (never a silent re-key, which would brick every stored ciphertext); a missing key file is generated once. This is the same construction S19's project-credential vault established (recorded there); S19's module is not on this branch's base, so the shape is restated here for provider keys — consolidation into one shared vault module is an integration-time cleanup the orchestrator can make when the sibling branches land.

**The AI SDK embed is the adapter seam (the issue's leverage note, read before design).** `ai` 7.0.157 with `@ai-sdk/openai` 4.0.105, `@ai-sdk/anthropic` 4.0.92, `@ai-sdk/google` 4.0.108, and `@ai-sdk/openai-compatible` 3.0.81 (all Apache-2.0, exact-pinned per E15) implements the provider-neutral seam: native OpenAI/Anthropic/Google factories take the key, organization, and project; Ollama rides `createOpenAICompatible` (the recorded leverage reading); custom headers are scanned for credential-shaped values (a bearer/Basic/token value shape, a session/auth/token cookie shape, or any header named like a credential) and REFUSED before any request is built — the API-key field is the only credential channel, recorded as the v1 prototype limitation for providers needing a custom auth header. Native protocols refuse a base URL (their endpoints are the protocol's own); ollama/openai-compatible require one. Request params ride the call verbatim.

**The connection test is ONE real minimal request, honest and redacted (AC10; UI_DESIGN S9's "must not always succeed" rule).** `runConnectionTest` sends a bounded deterministic prompt ("Reply with the single word: ok.", 16 output tokens, 15 s abort) through the SAME adapter seam runtime calls use, so it exercises reachability, authentication, and the model id at once. Success requires a completed request AND a response; every failure maps to a typed code (`PROVIDER_CONNECTION_TEST_UNREACHABLE|AUTH_FAILED|NOT_FOUND|FAILED`, `PROVIDER_CONFIG_INVALID`, `PROVIDER_CREDENTIAL_REVOKED`) with a redacted `safe_message` — never the key, never a response body, never a header dump; the display URL contributes its HOST only, userinfo and query stripped (G3). There is deliberately NO unconditional success path (pinned by a test that proves a refused adapter never yields success, plus the code shape: the success branch is only reachable after `generateText` resolves). G7: default CI answers the test route with LOCAL fake endpoints only (right key, wrong key, unreachable, no unconditional success); the LIVE check is the separately documented opt-in suite (`apps/user-runtime/live/providers-live.test.ts` + README) — outside every default vitest include pattern (a three-test pin asserts the exclusion and that the suite refuses to run without the owner's env), run manually with the owner's key, asserting the honest typed union either way and never printing the key.

**The D17/G4 gate is enforcement at the two boundaries where a model call would happen.** `ProviderGate` (composed ONLY under `providerEnforcement: true` — the real runtime posture, set by main.ts) refuses a `message.send` whose conversation has no usable provider BEFORE anything is written (the composer's explanatory state has a runtime backstop; the AC test pins the empty stream — nothing fabricated), and refuses a run start whose provider snapshot references a missing, disabled, or revoked-credential provider: the run is driven to FAILED with a typed `provider.configuration_refused` journal event on its own stream (provider id + code only — D26; no credential material, no response bodies — G3) and no worker ever spawns. Enforcement and the scripted reply producer are MUTUALLY EXCLUSIVE (a typed startup failure — the scripted producer fabricates completions, which is exactly what enforcement exists to prevent; the E2E mock keeps its own D51 mock-harness posture, never a fallback). The AC11 effective resolution is one honest union — the conversation override first, then the Agent's default pair, each resolved entry checked enabled + credentialed — answered at `GET /v1/providers/effective` and consumed by BOTH the header control and the composer.

**The HTTP surface crosses the credential exactly once per direction.** `POST /v1/providers` and `POST .../credential` accept the secret in the body and answer ONLY the masked view; no route echoes a credential; revoke/replace are the only lifecycle moves on a stored key (there is no read-back route to refuse — it does not exist). Every route is workspace-scoped (E12). The E9 platform provisioning route (`PUT /v1/providers/platform`) is deliberately NOT on the browser allowlist: admin provisioning writes through the loopback/internal channel at provisioning/top-up time, write-only, with a stable provider_id so a top-up REPLACES the credential instead of duplicating. The browser allowlist grows by exactly the user-facing surface: two GETs (masked catalog, effective readout) and six POSTs (configure, credential, revoke, status, test, override) — pinned by the contracts allowlist tests.

**The UI renders the runtime's truth, never a guess (G4/D17).** Settings → Providers & models (UI_DESIGN §S9) lists the masked catalog (name, protocol badge, origin badge, model, base URL, enabled/disabled chip, the masked hint or the honest "no key stored" / "No-key mode" states) with per-row actions: connection test (loading state "one real request is on its way", success with model + latency, or the typed redacted failure rendered verbatim), enable/disable, replace (inline masked form, "takes effect for the next call — no restart"), and revoke behind an armed confirm (no destructive click). The add-provider form carries every PRD §9 field: display name, protocol (which pre-selects no-key mode for local protocols), base URL, API key vs no-key mode (radio), model identifier, and the advanced disclosure with organization/project/headers/request-parameters; the credential field is a masked input accepted exactly once and cleared the moment the submit is raised — a failed configure asks the user to re-paste rather than the surface keeping a re-displayable secret (the G3-safe trade-off, recorded). The chat header's model control shows the effective provider · model with its source (Agent default vs conversation override), opens a panel that applies or clears the per-conversation override (enabled entries only, model pre-filled from the provider's default), and renders "No provider" with the runtime's own safe_message when unconfigured. The composer is gated by the same readout: an unconfigured resolution disables sending with the runtime's typed state verbatim, a still-resolving readout never offers a send, and only a configured resolution enables the composer (the S09 no-provider copy remains the unwired-caller fallback). Per-Agent default assignment lives on the D16 Agent settings surface: the default-provider editor offers the masked catalog as a select (any status — an Agent default may reference a temporarily disabled provider, which then resolves to the honest D17 state) with the manual-entry fallback when no catalog is wired. Below md the header control collapses (the 360px identity-priority contract from S12). Custody display rules are pinned: no password input ever renders a stored value, and no "show key" affordance exists.

## Alternatives considered (preserved)

- **A shared vault module with S19 now:** rejected on this branch — S19's vault is not on the branch base; restating the construction for provider keys and consolidating at integration keeps the branch honest without inventing a cross-branch dependency.
- **Storing the vault key in the composition's env:** rejected — the container-local 0600 key file IS the recorded prototype custody posture (D22's bootstrap key); an env var would put the key in process listings and compose files (G3 adjacency) without changing the trust boundary.
- **Letting the UI hold the credential until a successful configure (retry-friendly):** rejected — the surface would keep a re-displayable secret in client state; the G3-safe trade-off (clear on submit, re-paste on failure) is recorded above.
- **A provider/model "test" that pings a cheaper endpoint (models list) instead of a generate call:** rejected — a models-list 200 proves neither authentication-with-key-for-model nor that the model id resolves; the ONE minimal generate through the real seam is the honest test (and is what makes the typed AUTH_FAILED/NOT_FOUND classifications true).
- **Encrypting with a key derived from the workspace id (no key file):** rejected — a derivative of public-ish identifiers is not key material; the random 0600 file is the recorded posture.
- **Browser-allowlisting the platform provisioning route (for admin UI convenience):** rejected — E9 provisioning is admin-funded and write-only; the browser never needs it, and excluding it makes the custody surface structurally smaller (the same no-route reasoning as S18's no-takeover inventory).
- **Optimistic override application in the header (flip the label immediately):** rejected — the runtime's read-after-write effective answer IS the next truth (the S11 settings-surface pattern); the override POST returns the union and the query cache takes it, so the header never shows an unvalidated guess.
