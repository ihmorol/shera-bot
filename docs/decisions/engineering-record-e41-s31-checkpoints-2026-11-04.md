## Decision and rationale

**D33 checkpoints are DURABLE STATE + the journal marker, written in ONE transaction, at SAFE SEMANTIC BOUNDARIES ONLY — and the boundary vocabulary is CLOSED DATA, not convention.** The v21 `run_checkpoints` table (STRICT, append-only, keyed `(workspace_id, task_id, step_id, checkpoint_version)` — retaking appends a new version, recovery evidence is never rewritten) carries the full D33 field set (`task_id`, `step_id`, `checkpoint_version`, `completed_actions`, `pending_action`, `artifact_refs`, `provider_usage`, `lease_state`, `approval_state`, `external_effect_state`, `resume_instructions`, `created_at`; the JSON columns typed by shape CHECKs after the provider-catalog `headers_json` discipline; `lease_state`/`approval_state` CAPTURE the recorded S16 lease and S20 approval states — never a new mechanism). The v21 row and the task stream's `checkpoint.taken` contract envelope commit in ONE transaction (D23 rule 5) by the runtime's `CheckpointService`; idempotency is the deterministic event id (`evt_checkpoint_taken_<task>_<step>_v<n>` — a replayed step deduplicates at the journal, the winner's row is the contract, D23 rule 6); `checkpoint_version` is monotonic per task. The AC5 structural pin: the ONLY writer entry point validates the step kind against the closed `CHECKPOINT_STEP_KINDS` vocabulary — the seven D33 named boundaries (completed search, downloaded document, saved artifact, applied patch, completed test run, received approval, confirmed external request) PLUS `tool_execution`, the generic succeeded-tool boundary the recorded capability→kind mapping lands on (`research.search` → `completed_search`, `research.fetch`/`research.parse.document` → `downloaded_document`, everything else → `tool_execution`); a stream/token-style step is a typed `NON_SEMANTIC_STEP` refusal — no row, no journal event, structurally unrepresentable. AC5 end-to-end: a 50-frame `progress.reported` streamed run journals the lightweight between-checkpoint vocabulary and produces ZERO checkpoint rows and ZERO checkpoint markers (never per token, never on a timer). A SUCCEEDED tool execution IS a semantic boundary: the S21 executor offers it through a contained port (the writer validates; the port's failures never change the settled outcome), taking exactly one checkpoint per settled execution with the tool's identity and its DECLARED E13 class in `external_effect_state`.

**The E13 recovery classes drive restart recovery as fail-closed DATA — the same purity discipline as the S22 retry policy, and the runtime never guesses an effect safe to replay.** The pure decision (`decideRecovery`, `modules/recovery/recovery-driver.service.ts`): a pending action DECLARING `replayable` auto-resumes (the effect re-executes from the checkpoint — safe by declaration even doubled); `idempotent_retry` auto-resumes ONLY with its recorded idempotency key (the re-execution collapses under the SAME key — no key = unprovable dedupe = pause); `needs_human`, an UNDECLARED class (the E13 default), a missing pending action, or a missing checkpoint pauses `RECOVERY_REQUIRED` — the possibly-duplicated effect is NEVER replayed by the runtime. The class matrix pins one scripted case per class with an effect ledger: the replayable leg resumes without user action and the effect happens exactly ONCE; the idempotent leg pins the WORST case — the original effect LANDED before the interruption, the recovery re-execution carries the RECORDED key (a fresh key would double the effect — exactly what the pin forbids), and the net effect count stays ONE; the needs_human leg enters `RECOVERY_REQUIRED` with the ledger untouched and the resume port never called.

**The RecoveryDriver decides only what the checkpoints can vouch for, and the D8 walk stays the ONE machinery.** The driver's remit: runs left RUNNING (interrupted — after the boot reaper) and RECOVERY_REQUIRED. QUEUED is the S16 reconciliation's re-drive, RETRYING is the S22 coordinator's clock, PAUSED is a human/credits decision, terminals are closed, and a run with a LIVE worker row is skipped — someone's live work, the S16 conservative rule verbatim (the restart-matrix RED caught this hole before it shipped: without the skip, the boot walk paused a healthy run whose worker was alive). The resume legs walk `applyRowLifecycleTransition` — never a second state machine: an interrupted RECOVERY_REQUIRED run takes the runtime-actor `recovery_auto_resume` row (guarded by the checkpoint's recorded class — the authorization data lives in the chunk-1 record, not in the driver); an interrupted RUNNING run re-drives directly (already RUNNING — the state the worker works under). A `needs_human` RUNNING run takes the existing `recovery_required` row. Every decision journals a `recovery.decided` marker on the task stream (basis, reason, the recorded idempotency key — a token, not a secret, G3, `resume_from_checkpoint_version`, and the honest `replayed` flag; a port failure records `replayed: false` and the typed `resume_failed` outcome — the run stays RUNNING, exactly the interrupted state, and the next boot owns it again). The re-drive seam is the SAME supervisor startWorker the S16 QUEUED re-drive uses; a runtime without a worker system refuses the re-drive typed (G4: never a silent fake re-drive).

**The boot sequence is the recorded composition: the S16 worker reconciliation FIRST, then the S31 scan** (the reaper closes the worker-row truth; the driver decides what it left). The composed `recovery` handle exposes `bootPass` (the awaited boot entry — the in-flight promise is visible the moment compose returns, never a pre-resolved fake), `recoverInterruptedRuns()` for operators, `lastReport()`/`bootSettled()` for the status read. The restart matrix pins the whole §13 walk over a close-and-reopen restart (the same SQLite file, every service rebuilt — the durable state is exactly the rows and the journal): the journal and run rows byte-identical across the restart (E2/E10 retention, D26 replay); QUEUED runs re-driving through the S16 reconciliation; the interrupted run resuming from its LAST SAFE STEP (the marker's `resume_from_checkpoint_version` equals the checkpoint's version; the recorded `resume_instructions` ride); the ambiguous run pausing with the effect never replayed; Operation chat history and membership restoring; a pending approval surviving UNCHANGED (same request record, same reminder slots, still pending) with its WAITING_FOR_APPROVAL run untouched by the scan; schedules catching up EXACTLY ONCE across two boots (the S28 ledger pinned through the real `reconcileBoot` — never reworked); and the healthy-worker keep-alive leg (the AC25 automated leg, with the fake-worker re-drive spawning REAL children end-to-end in the composed boot test).

**The surfaces render the runtime's OWN records — the copy is basis-anchored by test.** The runtime read (`GET /v1/recovery/status`) assembles the S11 model from the journal and the D8 rows: `review_needed` (the RECOVERY_REQUIRED runs with the unprovable pending step and the recorded resume instructions), `resumed` (the last boot scan's auto-resumes), `timelines` (per run, the durable checkpoint → restart → resume/pause markers), and `workspace_state` (review_needed wins, then the unsettled-boot RECOVERING window, then the RESUMED transient, else idle). The top-of-app banner (S11: a strip, never a modal; idle renders NOTHING) renders the exact S11 copy — "Restoring your workspace…", "A task needs your review" with the Operation deep link — and the run cards render the timeline markers through the copy builders, the SINGLE source for every recovery string: the resume marker says "Resumed from last safe step — checkpoint v<n> (<step>)" and names the class that authorized it; the pause marker names what could not be proven safe and promises no outcome. The suite asserts the copy against the ACTUAL resume basis and bans the exact-resume claims AT THE SOURCE (a source-grep test over the three surface modules); the a11y suite's single-focus-treatment rule and the §2.3 icon+text pairing held (the banner declares no focus ring of its own; every state pairs an icon with its text). ## Alternatives considered (preserved)

- **Widening the human `recovery_resume` row's actors to include runtime:** rejected — the journal must never mistake a class-driven auto-resume for a human approval ("recovery_approved" would be a false record). A SEPARATE command (`recovery_auto_resume`, reason `recovery_class_permits`) keeps the audit trail honest; the transition-table comment's reserved-layer note is satisfied with its own recorded rationale.
- **Auto-resuming RECOVERY_REQUIRED runs unconditionally at boot:** rejected — fail-closed E13. A RECOVERY_REQUIRED run auto-resumes ONLY when its latest checkpoint's pending action declares a permissive class (with the key for `idempotent_retry`); anything the checkpoints cannot vouch for stays as-is (the S16 "left for the recovery slice" semantics preserved for exactly those runs).
- **Deduplicating recovery decisions per run in the driver (a once-ever resume):** rejected — multiple restarts legitimately re-decide; the once-per-boot discipline is the caller's (the scan visits each recovery-owned run exactly once per pass), and the per-effect safety is carried by the class semantics + the recorded idempotency keys, not by driver-call dedupe.
- **A new gateway-lifecycle "restart" event type for the timeline:** rejected for this slice — the reaper's `worker.reaped` (already journaled by S16) IS the restart evidence on the run's stream; a second marker would duplicate the same fact. The timeline renders checkpoint → worker.reaped (restart) → recovery.decided.
- **Serving the banner/timelines from web fixtures:** rejected — the surfaces read the REAL `/v1/recovery/status` (the runtime's own records); a fixture-fed banner could claim a recovery the runtime never decided (G4). The fixtures stay where the recorded mock-world discipline puts them (demo conversations), not on safety surfaces.
