## Decision and rationale

**1. Terminal records are one journal-shaped STRICT table behind a single writer.** v14 `terminal_events` stores each execution as an ordered record stream — one `started` row (command, working directory, resource policy, record-time approval state), `output` rows (redacted chunks, 8192-char cap), one `exit` row (code/signal) — keyed `(workspace_id, terminal_id, sequence)` with per-terminal 1-based gapless sequences and column-family CHECKs that make a misrecorded row unrepresentable (each kind carries exactly its own fields). `TerminalEventsRepository` is the only SQL home; writer-side rules refuse every dishonest shape (start after start, output/exit without start, anything after exit — an ended execution cannot grow new output). `TerminalRecorder` is the ONLY writer of rows and the ONLY producer of the `terminal.started|output|exited` journal vocabulary, committing the row and its journal entry in ONE transaction in BOTH failure directions (D10, pinned by rollback tests each way). Approval state is the record-time posture vocabulary `not_required|pending|approved|rejected` — recorded, never inferred from output text.

**2. The D14 gap is the slice's recorded condition, not a silent shortfall.** The D14 harness protocol has no terminal frame (verified: child→parent frames are hello/ready/heartbeat/token/completed/fatal/error), so nothing in the protocol stream can tell the runtime what shell command an Agent ran. What IS recorded today — through `observeSessionSpawnWithTerminalRecorder` on the session spawn seam — is the runtime's own harness launch: the substituted argv exactly as the OS receives it, the truthful working directory (the child inherits the runtime's; no cwd override exists at this seam), the supervision policy that actually bounds the child, and `os_resource_limits: null` because NO OS-level limit is enforced on session children in this slice (dressing up a limit would be a lie, G4); the child's stderr streams through the redaction boundary; the exit closes the record. Real Agent-initiated shell executions land with S26 writing through the same `TerminalRecorder` on `RuntimeHandle.terminals` — the boundary layer, vocabulary, and read-only surface are already its contract. Containment is structural: a recording failure is fault-logged and never costs the Agent its session.

**3. The browser service is one shared Chromium profile per container with a demand lifecycle.** Playwright `launchPersistentContext` on a container-local profile directory (the D22 custody store) — cookies and session state survive service AND runtime restarts because they live in the profile dir, not the process (AC19 partial; the composed runtime disposes the browser cleanly before shutdown so the profile flushes). Lifecycle: starts on demand for a capable caller only, idle-closes on a configurable timer (a viewer poll counts as activity — a watched browser is not idle), detects an outside-of-`dispose` close as `crashed`, and relaunches cleanly on the SAME profile dir at the next demand (all four states + restart pinned with real Chromium). `snapshotView` returns the ACTUAL current page — real URL, title, fresh JPEG screenshot — never a placeholder; a stopped/starting/crashed browser answers its true state with NO image and NO url (G4). **Recorded deviation from the issue's leverage note: screenshot-on-demand via `page.screenshot` instead of CDP `Page.startScreencast`** — the backend is GET-shaped; a push-frame panel is future work; CDP remains reachable through the driver seam (Playwright's `newBrowserCDPSession`, exercised in the crash test).

**4. Read-only is the route inventory, pinned at three layers.** The HTTP surface is exactly five GET routes (`/v1/terminals/events|state|:terminal_id`, `/v1/browser/view|state`); non-GET verbs answer the typed 404 because no mutation handler exists to hit; the contract allowlist (`isBrowserRuntimePath`) grows by exactly those five GETs, so a stdin write, a signal send, or a browser navigation is unreachable from the browser by construction; the UI adds structural read-only-ness (xterm `disableStdin` with no `onData` — no input path to remove; the browser URL bar is a display, not an input; the only button either panel can render is a read Retry). Enumerated-inventory tests pin both surfaces to the exact route lists, including a control-vocabulary scan (no navigate/click/type/keyboard/control paths). D6 conflict prevention: the browser has ONE control grant — `claimControl` refuses a second, different claimant with the typed `BROWSER_CONTROL_CONFLICT` (first owner untouched, pinned), same-owner re-assert is idempotent, and release is owner-only; the terminal has no control at all, so there is nothing to contest. The capability gate (D27) admits ONLY `browser-research` — a missing capability or any other kind (`code-execution` included) is refused typed before anything launches; the read-only view intentionally requires no capability (it is the user's panel, not a driver). S26 owns the full per-task capability-manifest enforcement behind this check.

**5. G3: secrets die at the boundary before any write.** `redactSecrets` is the single terminal-boundary authority (and the browser view's url/title pass through the same layer): PEM private-key blocks, Bearer tokens, Authorization headers, connection-string userinfo, and secret-vocabulary key assignments — quoted or bare, JSON/YAML/env/CLI shapes — collapse to `[REDACTED]` before the recorder builds any payload, so the persisted rows, the journal entries, and the post-commit WS broadcast are clean by construction. The layer errs toward over-redaction, and the review round closed two real holes: JSON-style QUOTED keys (`"api_key": "..."` previously LEAKED — the key span's charset excluded quote characters) and `cookie` missing from the vocabulary (an echoed `set-cookie:` header leaked the cookie value; AC4 names cookie values explicitly). Automated redaction evidence: per-family pins plus an end-to-end test that drives a real cookie-setting page through the composed runtime and scans every API payload, the `runtime.db` AND its WAL at the byte level, and every fault-log line for the cookie value; the profile directory is the only place session state exists (D22).

**6. The web panels ride the existing transports — no new write path exists client-side.** The Terminal tab subscribes the per-Agent `terminal:<workspace_id>:<agent_id>` journal stream over the S09 gateway's read-only `stream.subscribe`/`replay.request` (workspace-bound; the pure reducer dedupes exactly-once on the per-stream sequence, the cursor acknowledgement trails the render per E10, reconnect replays only the gap) and renders an append-only xterm.js viewport (client-only, themed entirely from CSS custom properties — the token layer stays the only owner of raw values), the D35 execution card (command/workdir/policy/approval badge, verbatim from the journal), earlier-execution history, and the honest Live/Reconnecting/Offline delivery states. The Browser tab polls the two GETs (4s view / 10s state, paused on hidden tabs, stale-honest via the captured-at stamp) and folds them through `browserTabState` — before any view read lands, the state readout fills the honest answer (unconfigured or the true lifecycle); a running browser whose first capture is still in flight stays on the loading skeleton. Both tabs sit in the S7 order (Files, Editor, Terminal, Browser, Private files, Artifacts) and reach the API only through the five allowlisted GETs.

**7. E-note (OSS leverage, E15 policy):** adopted `@xterm/xterm` 5.5.0 (MIT) and `@xterm/addon-fit` 0.10.0 (MIT) in apps/web, and `playwright` 1.64.1 (Apache-2.0, on the S01 license allowlist — inventory green; **this corrects the earlier note that called Playwright MIT**) in apps/user-runtime; all three EXACT-pinned per the E29 CodeMirror precedent. `node-pty` (the issue's other embed suggestion) is NOT adopted: the prototype has no user-side terminal, and a PTY would fabricate an input path (G6) — revisit only if a future slice records a user-side terminal scope. OpenHands' read-only live-view composition (MIT) informed the panel structure as a pattern, not code.

## Alternatives considered (preserved)

- **CDP `Page.startScreencast` push frames (the issue's embed suggestion):** superseded by screenshot-on-demand — the transport and API are GET-shaped this slice; a push-frame panel needs its own transport decision and is future work. CDP reachability is preserved at the driver seam.
- **`node-pty` for the terminal panel:** rejected — the panel renders what the runtime's own children emit; a PTY would create an interactive input channel the product must not have (PRD §4.3/§20: no takeover).
- **Screencast-style WS fanout for browser frames:** rejected for now — polling GETs keep the browser surface read-only-by-shape and the states honest; a fanout surface would need its own redaction pass for frames.
- **Storing screenshots:** rejected — the view is served as captured and never persisted anywhere by the module (the DB byte-scan test pins the DB stays clean); freshness is the poll's job.
- **Duplicating the browser control boundary into the API:** rejected — control-shaped operations exist ONLY at the service's driver seam (runtime code); the API surface has no control arm at all, which is what makes the no-takeover AC structural rather than a permission check.
- **A shared stream-naming constant in packages/contracts:** the web client mirrors `terminal:<workspace_id>:<agent_id>` locally, the same convention as the conversation stream mirror (`conversation:<id>`); the runtime module remains the single runtime-side definition, pinned by a web test that asserts the convention.
