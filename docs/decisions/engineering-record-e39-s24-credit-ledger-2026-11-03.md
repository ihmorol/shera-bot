## Decision and rationale

**The ledger is implemented BEHIND the recorded seams, and the seams are the only funders.** The S28 fire pipeline claims its occurrence and calls the credit-reservation seam (claim → reserve → gate → run → walk → settle) — a refused reservation pauses the run BEFORE anything executes, exactly the posture E37 recorded as a seam against the then-nonexistent ledger; this slice is the ledger that seam consults. The S32 top-up writes its durable central grant record and then applies the D8 `resume_task` — the resume re-drive now lands on real balance (AC2), and the S32 record's "the grant record IS the seam S24 will consult" is fulfilled without changing S32's contract. The S22 cancellation path requests the reservation release through the recorded `credit_reservation_release_requested` hook into `releaseForRun` (`task_cancelled` reason). There is NO second funding or spending path: the browser trust boundary grows by exactly two GET reads (`/v1/credits`, `/v1/credits/runs/:run_id`) — no mutation route exists on the credits surface BY CONSTRUCTION (grants ride S32's authenticated control-plane seam; reservations/settlements ride the runtime's own model-call legs), pinned by the runtime-access contracts suite. The actor binding for the reads is server-side; the browser client sends no actor (the S20/S23 convention).

**The ledger model is boring on purpose (the issue's recorded leverage note: write it boring; explicitly do not adopt a billing library).** Migration v20 adds seven STRICT tables — `credit_account` (one row per workspace; non-negative `granted`/`charged`/`reserved` counters CHECK-constrained at the storage layer), `credit_transaction` (the append-only movement rows: `grant`, `reservation_hold`, `settlement_charge`, `reservation_release`, `adjustment` with `corrects_transaction_id`), `usage_record` (tokens/latency per call, platform AND custom providers), `cost_estimate`, `reservation`, `settlement`, `release`. The available balance is DERIVED (`granted − charged − reserved`), never a stored column that could drift from its parts; an under-estimate may honestly overdraw the derived balance, and that negative available is exactly what the next reservation refusal reads (no hidden clamp). Reserve→settle→release runs in ONE SQLite transaction per movement (D10): the settlement row, the release row, both movement rows, the reservation's status transition, and the account delta commit together; a reservation that is not actively held is refused typed (exactly-once settlement). Settlement charges the ACTUAL usage: over-estimate releases the remainder with reason `unused_estimate` (the release row is its own record), under-estimate charges the actual (D20's over-estimate/under-estimate cases pinned, including the property-style test over random usage distributions — 10 settlement-math tests).

**AC9's append-only guarantee is structural: the ledger has no UPDATE path.** Corrections are NEW `adjustment` rows that reverse up to the corrected row's account effect (`correctTransaction`: charge corrections reduce `charged`, grant clawbacks reduce `granted`; an over-reversal past zero is unrepresentable through the counters' CHECKs and refused typed at the row bound). The drill-down's `charged_units` is the net of settlement charges minus charge-reversing corrections — the ledger's own identity, computed in `runCost`, never recomputed anywhere else.

**D48 semantics are pinned as the pause, not the queue (AC1).** A refused reservation transitions the run to `paused` with `pause_reason = insufficient_credits` — asserted by a contract test that also pins it is explicitly NOT `QUEUED` (E1's capacity queue exists for resource exhaustion; the two mechanisms do not share a state). Before a top-up the run stays visibly paused with a notification through the recorded pause surfaces; after the admin top-up (the S32 grant + D8 resume) the run re-drives and completes (AC2's integration test drives grant → resume → completion through the real machinery). The pause is visible in three places: the run's pause state, the schedules surface's D48 pause reason (E37's), and this slice's exhausted-credit pause card with its unblocking paths in product language (an administrator top-up resumes paused runs; or cancel them from their Operation chat) plus the live count of triggers paused for credits — read from the SAME cached schedules query, never a second source.

**E13's ambiguous outcomes hold their reservation.** A platform-provider call whose outcome is unknown (timeout after send — the provider may or may not have processed the request) does NOT retry and does NOT silently release: the outcome is recorded on the run's stream (`run.credit_outcome_ambiguous`) and the run enters the E13 recovery class (`RECOVERY_REQUIRED`) with the hold standing — the recovery slice settles or releases it through the same typed seams. The clean-failure complement is pinned: a provider failure where the request never landed RELEASES the reservation (reason `provider_failure`).

**AC7: credits gate model calls ONLY.** A fully exhausted account (zero available) runs a no-model-leg plan to completion — the tool leg through the S21 executor, file writes, and approvals are unaffected (D20: prototype accounting never authorizes or gates a tool, a side effect, or spending). Custom-provider calls consume zero Shera credits but still record usage and latency locally with `charged_units = 0` (AC5, D20) — the UI's custom-provider section renders the zero as the point ("never consume Shera credits").

**The UI truth legs (AC8) — the numbers ARE the ledger's record.** The sidebar credits pill renders the remaining number with the reserved amount on hover AND on keyboard focus (`group-focus-within` mirrors the hover path — hover is never the only way to the number; the screen-reader text always carries both numbers, and color is never the only signal: the exhausted pill names its unblocking path in words). The S9 "Model budgets / Credits" settings surface shows the remaining/reserved/used-this-month headline row (the ledger's own numbers, never recomputed client-side), the per-run drill-down (picker rows are the ledger's runs-with-movements; a run's detail lists ITS OWN movement rows verbatim), the custom-provider usage block, and the exhausted-credit pause card that LEADS the surface when it applies (D48: distinct, visible, with what to do next). A not-yet-provisioned account says so instead of fabricating a zero balance (G4); before the container is ready the pill renders nothing (never a fabricated balance). AC8's "sums exactly to the ledger" is pinned NUMERICALLY on rendered output, not by copy: the UI test parses the rendered movement rows and asserts the ledger's identity (Σ settlement charges − Σ charge-reversing corrections = the charged number the header displays; every movement row renders verbatim — none dropped, none altered; the run rows' charged numbers sum to the account's charged total), including a corrected-charge scenario (the correction renders as its own appended row and the header shows the NET).

## Alternatives considered (preserved)

- **An OSS billing/debits library:** rejected — the issue's recorded leverage note says explicitly do not adopt one; the ledger is seven boring STRICT tables and one transaction flow.
- **A stored `available` balance column:** rejected — a derived value can drift from its parts; `granted − charged − reserved` from CHECK-constrained counters cannot (and the honest overdraw on an under-estimate needs to be representable, which a clamped stored column would hide).
- **A browser mutation route for top-ups (POST /v1/credits):** rejected — a parallel funding path next to S32's authenticated control-plane seam; the browser allowlist grows by GET reads only, by construction.
- **UI-side balance math (deriving remaining from granted/charged in the client):** rejected (G4) — the UI renders the ledger's own wire numbers; the reconciliation identity lives in `runCost` alone, and the UI test verifies the RENDERED rows against it instead of recomputing it.
- **Default-selecting the first run in the drill-down:** rejected — a selection the user did not make would render numbers nobody asked for; the detail renders only a selected run (the capture harness clicks the row it asserts against).
- **Retry-with-backoff for ambiguous provider outcomes:** rejected — E13 forbids the blind retry of an outcome that may have landed; the hold stands into recovery instead.
- **Per-component focus rings (the WIP's `focus-visible:outline` utilities):** rejected — the a11y suite's structural pin makes the global `:focus-visible` rule the single treatment; redeclared rings are dead code that shadows the token rule.
- **Rendering the estimated cost next to the settled cost in the drill-down:** deferred — the estimate row exists in `cost_estimate`, but the S9 spec's drill-down is the ledger's own rows; estimate display belongs with the launch-preview surface (D30/E28's recorded estimate formula), not a second estimate UI here.
