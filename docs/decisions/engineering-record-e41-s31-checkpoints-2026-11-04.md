## Decision and rationale

**D33 checkpoints are DURABLE STATE + the journal marker, written in ONE transaction, at SAFE SEMANTIC BOUNDARIES ONLY — and the boundary vocabulary is CLOSED DATA, not convention.** The v21 `run_checkpoints` table (STRICT, append-only, keyed `(workspace_id, task_id, step_id, checkpoint_version)` — aligned with the writer: the SAME step_id deduplicates (D23 rule 6) and a NEW version arises for a NEW step id, so taken evidence is never rewritten) carries the full D33 field set (`task_id`, `step_id`, `checkpoint_version`, `completed_actions`, `pending_action`, `artifact_refs`, `provider_usage`, `lease_state`, `approval_state`, `external_effect_state`, `resume_instructions`, `created_at`; the JSON columns typed by shape CHECKs after the provider-catalog `headers_json` discipline; `lease_state`/`approval_state` CAPTURE the recorded S16 lease and S20 approval states — never a new mechanism). The v21 row and the task stream's `checkpoint.taken` contract envelope commit in ONE transaction (D23 rule 5) by the runtime's `CheckpointService`; idempotency is the deterministic event id (`evt_checkpoint_taken_<task>_<step>_v<n>` — a replayed step deduplicates at the journal, the winner's row is the contract, D23 rule 6); `checkpoint_version` is monotonic per task. The AC5 structural pin: the ONLY writer entry point validates the step kind against the closed `CHECKPOINT_STEP_KINDS` vocabulary — the seven D33 named boundaries (completed search, downloaded document, saved artifact, applied patch, completed test run, received approval, confirmed external request) PLUS `tool_execution`, the generic succeeded-tool boundary the recorded capability→kind mapping lands on (`research.search` → `completed_search`, `research.fetch`/`research.parse.document` → `downloaded_document`, everything else → `tool_execution`); a stream/token-style step is a typed `NON_SEMANTIC_STEP` refusal — no row, no journal event, structurally unrepresentable. AC5 end-to-end: a 50-frame `progress.reported` streamed run journals the lightweight between-checkpoint vocabulary and produces ZERO checkpoint rows and ZERO checkpoint markers (never per token, never on a timer). A SUCCEEDED tool execution IS a semantic boundary: the S21 executor offers it through a contained port (the writer validates; the port's failures never change the settled outcome), taking exactly one checkpoint per settled execution with the tool's identity, its DECLARED E13 class, and the tool's runtime-verified risk class in `external_effect_state` — and, since the fix round, the pending action RECORDED FOR REAL (kind `tool_execution`, the tool id, a writer-bounded summary, the declared class, the runtime-derived idempotency key for an `idempotent_retry`, the risk class — all RUNTIME data from the resolved definition and the execution record, never from the tool result).

**The E13 recovery classes drive restart recovery as fail-closed DATA — the same purity discipline as the S22 retry policy, and the runtime never guesses an effect safe to replay.** The pure decision (`decideRecovery`, `modules/recovery/recovery-driver.service.ts`): a pending action DECLARING `replayable` auto-resumes (the effect re-executes from the checkpoint — safe by declaration even doubled); `idempotent_retry` auto-resumes ONLY with its recorded idempotency key (the re-execution collapses under the SAME key — no key = unprovable dedupe = pause); `needs_human`, an UNDECLARED class (the E13 default), a missing pending action, or a missing checkpoint pauses `RECOVERY_REQUIRED` — the possibly-duplicated effect is NEVER replayed by the runtime. **The trust boundary caps every declaration (the fix round's decision — see the section below): the effective class is the declared class ONLY when the record's runtime-verified `risk_class` is READ_ONLY; a non-read-only (or risk-unknown) declaration is needs_human REGARDLESS of what it declares.** The class matrix pins one scripted case per class with an effect ledger: the replayable leg resumes without user action and the effect happens exactly ONCE; the idempotent leg pins the WORST case — the original effect LANDED before the interruption, the recovery re-execution carries the RECORDED key (a fresh key would double the effect — exactly what the pin forbids), and the net effect count stays ONE; the needs_human leg enters `RECOVERY_REQUIRED` with the ledger untouched and the resume port never called; the capped legs (a WRITE/EXTERNAL tool declaring `replayable`, with and without a recorded key) pause with reason `risk_class_caps_recovery`.

**The RecoveryDriver decides only what the checkpoints can vouch for, and the D8 walk stays the ONE machinery.** The driver's remit: runs left RUNNING (interrupted — after the boot reaper) and RECOVERY_REQUIRED. QUEUED is the S16 reconciliation's re-drive, RETRYING is the S22 coordinator's clock, PAUSED is a human/credits decision, terminals are closed, and a run with a LIVE worker row is skipped — someone's live work, the S16 conservative rule verbatim (the restart-matrix RED caught this hole before it shipped: without the skip, the boot walk paused a healthy run whose worker was alive). The resume legs walk `applyRowLifecycleTransition` — never a second state machine: an interrupted RECOVERY_REQUIRED run takes the runtime-actor `recovery_auto_resume` row (guarded by the checkpoint's recorded class — the authorization data lives in the chunk-1 record, not in the driver); an interrupted RUNNING run re-drives directly (already RUNNING — the state the worker works under). A `needs_human` RUNNING run takes the existing `recovery_required` row. Every decision journals a `recovery.decided` marker on the task stream (basis, reason, the recorded idempotency key — a token, not a secret, G3, `resume_from_checkpoint_version`, and the honest `replayed` flag; a port failure records `replayed: false` and the typed `resume_failed` outcome — the run stays RUNNING, exactly the interrupted state, and the next boot owns it again). The re-drive seam is the SAME supervisor startWorker the S16 QUEUED re-drive uses, and the recorded idempotency key rides the worker spec (`recoveryRedriveSpec` → `spec.config.recovery_idempotency_key` — the re-execution lands under the SAME key the original consumed); a runtime without a worker system refuses the re-drive typed (G4: never a silent fake re-drive — the composed no-worker leg pins the typed `resume_failed`, never a fake resumed).

## Decision — the recovery trust boundary (the fix round; G6 applied to recovery)

**Only a runtime-verified READ_ONLY tool may auto-resume; a non-read-only declaration — however friendly — always pauses `RECOVERY_REQUIRED`, and awaits a recorded owner decision before it ever becomes executable.** This is the D35 ladder applied to recovery, and it is G6's "agents never self-approve" made concrete: tools-inventory stores an agent-DECLARED E13 recovery class verbatim, so the declared class alone can never authorize a re-execution. The writer records BOTH the declared class AND the tool's runtime-verified `risk_class` (from the resolved definition — never from the tool result, never from the proposal string); the pure decision (`decideRecovery`) caps: effective class = declared class ONLY when `risk_class === "READ_ONLY"`; for every other risk class — or a record missing the risk class entirely (the record must PROVE read-only) — the effective class is `needs_human`, with the pause reason `risk_class_caps_recovery` naming the cap. A malicious WRITE tool declaring `replayable` therefore pauses at every restart instead of blind-re-executing; the class matrix pins the cap five ways (the pure policy: capped replayable, capped idempotent_retry WITH a recorded key, capped missing-risk; the affirmative READ_ONLY legs) and the composed boot walk pins it end-to-end: the first gateway REALLY executes both an agent-created READ_ONLY `replayable` tool (auto-resumes through the real supervisor) and an agent-created EXTERNAL_WRITE tool declaring `replayable` (pauses with the cap reason; no worker ever spawns). E13's class semantics remain the recorded vocabulary; this decision BOUNDS what a declaration may do until an owner records otherwise — widening auto-resume to any non-read-only class is a product decision this record explicitly does not make.

## Alternatives considered (preserved)

- **Widening the human `recovery_resume` row's actors to include runtime:** rejected — the journal must never mistake a class-driven auto-resume for a human approval ("recovery_approved" would be a false record). A SEPARATE command (`recovery_auto_resume`, reason `recovery_class_permits`) keeps the audit trail honest; the transition-table comment's reserved-layer note is satisfied with its own recorded rationale.
- **Auto-resuming RECOVERY_REQUIRED runs unconditionally at boot:** rejected — fail-closed E13. A RECOVERY_REQUIRED run auto-resumes ONLY when its latest checkpoint's pending action declares a permissive class (with the key for `idempotent_retry`); anything the checkpoints cannot vouch for stays as-is (the S16 "left for the recovery slice" semantics preserved for exactly those runs).
- **Deduplicating recovery decisions per run in the driver (a once-ever resume):** rejected — multiple restarts legitimately re-decide; the once-per-boot discipline is the caller's (the scan visits each recovery-owned run exactly once per pass), and the per-effect safety is carried by the class semantics + the recorded idempotency keys, not by driver-call dedupe.
- **A new gateway-lifecycle "restart" event type for the timeline:** rejected for this slice — the reaper's `worker.reaped` (already journaled by S16) IS the restart evidence on the run's stream; a second marker would duplicate the same fact. The timeline renders checkpoint → worker.reaped (restart) → recovery.decided.
- **Serving the banner/timelines from web fixtures:** rejected — the surfaces read the REAL `/v1/recovery/status` (the runtime's own records); a fixture-fed banner could claim a recovery the runtime never decided (G4). The fixtures stay where the recorded mock-world discipline puts them (demo conversations), not on safety surfaces.
- **Reading the declared class alone at the decision layer (no risk-class cap):** rejected (the security review's headline) — the declared class is AGENT-controlled data; honoring it for WRITE/EXTERNAL tools would let a malicious tool declare `replayable` and blind-re-execute at every restart. The cap (declared class honored only under a runtime-verified READ_ONLY risk class) keeps the auto-resume reachable for the honest case and fail-closed for the untrusted one.
- **Writing the pending action only when the tool result declares it:** rejected — the tool result is untrusted surface; the pending action's recovery data comes from the RESOLVED DEFINITION and the execution record (the runtime's own), never from the result.
- **An agent-chosen idempotency key:** rejected — a chosen key could collide to suppress effects; the key is derived by the runtime from the execution identity (tool id + journalled args digest), deterministic and bounded.
- **Skipping the class recording for non-READ_ONLY tools entirely:** rejected — the declared class and the risk class stay on the record even when capped, so the review surface and a future owner decision see exactly what was declared and what bounded it (the honest audit trail; G6 does not mean erasing the declaration).
