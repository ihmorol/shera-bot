## Decision and rationale

**Supervision policy constants are programmatic defaults, now env-tunable.** `DEFAULT_SESSION_POLICY` (`apps/user-runtime/src/modules/sessions/session-supervisor.service.ts`) pins the D32/D14 policy: idle hibernate after 120 s; heartbeat cadence 5 s with a 3-missed-interval window (15 s of silence ⇒ hung — a slow-but-healthy child keeps beating and is never killed); handshake backstop 10 s; up to 3 supervised crash-restarts per 60 s window (the crash beyond is terminal `failed` — crash-looping is not "recovered"); protocol violations capped at 3+1 per incarnation (one post-cap restart, then terminal `failed`); escalation cadence shutdown frame → SIGTERM at 2 s → SIGKILL at 1 s further; per-incarnation stderr forwarding bounded at 8 KiB (the sink owns redaction, G3). Chunk 4 exposes four knobs through the SAME config seam as the harness command (`SHERA_SESSION_IDLE_HIBERNATE_MS`, `SHERA_SESSION_HEARTBEAT_INTERVAL_MS`, `SHERA_SESSION_MISSED_HEARTBEAT_LIMIT`, `SHERA_SESSION_HANDSHAKE_TIMEOUT_MS` in `apps/user-runtime/src/main.ts`), each validated against a documented sane range with a typed startup failure on garbage (G4) — a value in the wrong unit can never half-apply. The knobs are validated even with no harness configured, so a later-enabled harness cannot inherit an unchecked value. Explicit programmatic `sessionPolicy` overrides win wholesale (the `sessionHarness` seam rule). Rationale for env knobs: the honest way to tune deployments AND the only way to demonstrate hibernation at browser-evidence timescales (45 s idle, 1 s heartbeat in the captures).

**The spawn seam is one adapter; the harness command is configuration.** `apps/user-runtime/src/adapters/process/session-process-spawn.ts` is the ONLY production file that may import `node:child_process` for sessions (boundary guard PROCESS_BOUNDARY; the D14 fake Pi and the demo reply child are named test-infra exceptions). It adapts a configured harness command into the supervisor's `spawnChild(request)` contract: `{session_id}` / `{heartbeat_interval_ms}` placeholders in `SHERA_SESSION_HARNESS_ARGS` are substituted per spawn (never a shell, G3/G4), and the D15 compact session context travels through the `SHERA_SESSION_CONTEXT` environment variable — never argv, which is world-readable. Spawn-level failures (ENOENT/EACCES) surface as recorded crash events and a terminal session, never a silent hang. The supervisor owns protocol classification, escalation, and persistence; the adapter owns only process mechanics.

**Session replies are durable, idempotent, and serialized.** The `SessionReplyBridge` turns a committed user message into a supervisor prompt and publishes the reply through `conversations.executeCommand("message.send")` with idempotency key `session-reply-<trigger event_id>` (`apps/user-runtime/src/modules/sessions/session-reply-bridge.ts`): the reply is a journal event like any other — replayable on refresh, serialized per conversation by the conversation command path, and immune to redelivery duplication (a redelivered trigger computes the same key). The prompt text itself is never logged (G3).

**Presence is a polled read model — no WebSocket fanout (documented limitation).** The agent API reports `session.presence` (`none` | `starting` | `active` | `hibernating` | `restarting` | `failed`) on every roster and detail row, read from the supervisor's in-memory records; nothing is fabricated when the supervisor is disabled (`none` everywhere, G4). The web header polls the agent detail read every 5 s (`apps/web/lib/session-presence.ts`, `useAgentSessionPresence` in `apps/web/lib/agent-data.ts`), pausing entirely while the tab is hidden. **Live presence fanout is deliberately deferred**: session state changes are low-frequency, the poll keeps the transport surface unchanged (no new socket rooms, no replay semantics to design), and a fanout channel would need its own recovery story. The limitation is recorded here and at the poll site; a session-event stream should arrive with the Operation/live-supervision slices rather than grow ad hoc.

**Single global harness knob vs D51 per-Agent selection — DEFERRAL.** D51 wants per-Agent harness selection; the pack field exists since S10. This slice ships ONE global env knob (`SHERA_SESSION_HARNESS_COMMAND` + optional `_ARGS`) as the bootstrap: the supervisor, protocol, and reply bridge are harness-agnostic, so per-Agent selection is a compose-time routing change, deferred to the providers slice where per-Agent provider/model configuration lands with it. Rationale: two configuration dimensions arriving together would double the test matrix of the session slice without a consumer for the second axis.

**Disabled-supervisor fallback keeps the scripted streamer (G4).** With no harness command configured, no process ever spawns, presence is `none` everywhere, and the send path is byte-identical to S09/S11. The scripted reply producer remains compose-OPT-IN only (`scriptedReplies`), used by the E2E mock; `startRuntimeNode` never sets it, so enabling the supervisor cannot double-reply. Presence polling reuses the existing agent detail read (whose get-or-create side effect is journaled and idempotent — E24's documented GET side effect), so polling adds no new write path.

**The chat header renders presence honestly.** The S11 placeholder is retired. The chip renders every supervisor state with its own styling (loading pulse; starting/active live-green; hibernating muted; restarting amber; failed red — `motion-reduce:animate-none` on the pulsing dots); presence `none` renders NO chip and a failed presence read renders NOTHING scary (a presence indicator never becomes an error surface — G4). The first-time note (issue requirement) shows ONCE per browser session the first time an Agent's session goes live, dismisses itself after a pinned 8 s or on the next message, lives in a persistent `aria-live="polite"` region, and shows nothing at all when storage is unavailable (the "once" promise cannot be kept without it). The demo's derived pill is unchanged; real presence never leaks onto demo rows.

## Alternatives considered

- WebSocket fanout for presence now was rejected: it adds a second live semantic (rooms + replay) for a low-frequency read; the poll is honest and removable. Recorded as the deferral above.
- Validating policy knobs only when a harness is configured was rejected: garbage values would surface only after an operator enables supervision — the failure belongs at startup.
- Parsing the D15 context from argv was rejected by D15/G3 already; the adapter passes it via `SHERA_SESSION_CONTEXT` and the demo child decodes it to prove the channel.
- Writing reply text into the journal directly (bypassing `message.send`) was rejected: it would create a second conversation-mutation path and lose per-conversation serialization and idempotency.
- A per-Agent harness map in the env (e.g. `SHERA_SESSION_HARNESS_<AGENT>`) was rejected as unreadable/undebuggable; per-Agent selection belongs in the pack/provider configuration layer (D51) at the providers slice.
- Driving the browser evidence with the fake Pi's synthetic tokens (`t1t2t3`) was rejected for the captures: a scripted, human-readable reply (committed `demo-reply-child.ts`, test-infra only, shebang-executable, never referenced by production code) makes the chat exchange legible in evidence while speaking the same D14 protocol.
