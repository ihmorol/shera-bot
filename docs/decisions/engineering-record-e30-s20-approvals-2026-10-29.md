## Decision and rationale

**The approval lifecycle is runtime-owned end to end, and the browser can only speak through session-bound routes.** A typed `tool.proposed` proposal (D34 vocabulary, riding the D26 journal-registry path) whose risk class is gated (everything except READ_ONLY) creates the `ApprovalRequest` (G3: `args_digest` only, never raw arguments; free-text side-effect and resource-scope fields pass a deterministic redaction pass before any row or journal write), emits `approval.requested`, and pauses the run via the pre-existing D8 `request_approval` transition (actors: runtime). The withheld execute callback is stored with the in-memory run projection and runs only after an approve decision's transaction commits — nothing executes pre-decision (pinned by a side-effect sentinel test).

**The five choices are contracts constants rendered verbatim; only three create grants.** `approve-this-execution-only` → one-time grant pinned to the requester's principal and exact `args_digest`; `always-approve-this-tool` → reusable task-principal grant; `always-approve-this-tool-for-this-agent` → reusable agent-principal grant; `reject-this-action` resumes the run as an action denial without executing; `cancel-the-task` cancels the run AND its non-terminal children in the same transaction (D32's "never killed for capacity" untouched — this is an explicit user cancellation). Grant creation exists in exactly one place, inside the runtime transaction behind actor refusals; principal identity always derives from the stored request, never from wire input. `AGENT_CANNOT_SELF_APPROVE`/`AGENT_CANNOT_DECIDE_APPROVAL` are checked BEFORE status checks (absolute G6 ordering, pinned); decisions are immutable (repository guard + in-transaction re-check) and replay-safe (`already_decided` carries the stored resolution; cross-tab propagation is the visibility-driven 5s poll, pinned by source-level tests).

**AC26: the grant skips the prompt, never the check.** `checkExecutionAllowed` is the fail-closed gate every execution consults: strict zod input (malformed → typed throw, never default-allow), then grant lookup on the injected clock (revocation, expiry, principal, tool+version, capability, resource scope), then the grant's conversation scope against the acting conversation, then one-time consumption state. Pinned: revoke-mid-flight → refused; changed tool version → refused; changed args digest → refused; consumed one-time grant → refused even with identical args, including across a database reopen. One-time consumption is durable (`consumed_at`, v11) and stamped exactly once (`WHERE consumed_at IS NULL`) after the approved execution's callback resolves — the recorded trade-off (documented in code): a hard crash in the window after the side effect but before the stamp leaves the grant unconsumed; the alternative (pre-execution consumption) would burn the grant on a failed side effect. The window is fail-closed in the safe direction for the approval record (the request stays approved; the action is not re-executable through re-decision — `already_decided`).

**Reminders (E3) are durable rows, fired by scan, never state-mutating.** All five slots (0/15m/45m/3h/24h — contracts constants) are scheduled at proposal time on the injectable clock; `dueReminders(workspace)` stamps `delivered_at` write-once and reports `delivered`/`muted` outcomes; mutes (`approval`/`task`/`all`) suppress delivery only — the run stays paused and the approval stays visible (pinned). There is no runtime-side periodic scheduler yet: the tick is `POST /v1/approvals/due-reminders` (changed from GET in the security fix round — a state-stamping scan must not be a GET), polled by the UI on the app's 5s visible-tab cadence; a gateway-side scheduler is a recorded follow-up.

**The browser path is session-bound (the security P1 fix).** The local API's actor model is request-carried (a systemic, pre-S20 property). For this slice's two decision-shaped mutations the web proxy overrides the client-asserted actor with the authenticated session identity: `decided_by` on decisions and `created_by` on mutes are rebuilt server-side from the session (`SESSION_ACTOR_BINDINGS` table in the proxy); a body-asserted identity cannot reach the runtime through the browser path (pinned at the proxy layer). Direct runtime-API callers keep body relay — the documented systemic exception, unchanged by this slice. Mutes now carry their creator (v12 `approval_mutes.created_by`) and refuse non-user actors.

**The trigger rides the real harness seam, not a test backdoor.** `scriptedToolProposal` (opt-in compose wiring, G4 scripted streamer family) emits a journalled `tool.proposed`; a delegate on `HarnessRunService` fires only on a freshly-journalled proposal; capability/risk-class/resource-scope/side-effect come from the runtime-owned typed tool definition (D38) — a proposal the definition doesn't name is fault-logged and left un-gated, never classified (G2). The pause commits inside `startRun`'s atomic unit; read-only proposals run through (G6). Combining a custom `harnessAdapter` with `scriptedToolProposal` fault-logs the dropped proposal instead of failing silently.

**UI:** in-thread D9 card (exact tool+version, digest presence, target, side effect, risk badge, requesting Agent, scope, honest null expiry, five-slot reminder timeline), Radix decision modal with focus trap, five choices as the only initially focusable actions, `aria-live="assertive"` announcement, mute controls with notification-only copy, Settings → Permissions & approvals listing active grants (scope, tool+version, expiry, created by) with immediate-effect revoke, and a quiet "Decision recorded" state after an in-tab decision. Eleven live-browser captures at 360/768/1440 including keyboard-focus; the five choice labels are verbatim contracts constants — zero copy deviation.

## Alternatives considered (preserved)

- **BullMQ/Redis delayed jobs for reminders (the issue's embed suggestion):** rejected per E27 (D10/PRD §17 — no Redis in the prototype stack); durable rows + injected clock achieve the same schedule with restart-surviving state and no new infrastructure.
- **A dedicated `approval.decided` event type:** not available without a contracts change (frozen boundary); decisions are journalled as the D8 lifecycle events (`task.approval_granted`/`approval_rejected`/`cancelling`/`cancelled`, each carrying `approval_id`) plus the immutable request row. Reminder delivery is the write-once `delivered_at` stamp (no honest journal vocabulary for it); both recorded for the contracts-owning slice.
- **Runtime-side columns inside contracts:** rejected — v10 (`args_digest`) and v11 (`consumed_at`) extend the runtime's `ApprovalGrantRecord` beyond the contracts `ApprovalGrant` shape; contracts stay untouched.
- **GET for the reminder tick:** superseded by the security review — a state-stamping scan behind an unauthenticated-origin-able GET was a drive-by delivery-burn vector; it is a POST with a workspace-scoped body.
- **Pre-execution one-time consumption:** rejected — burns the grant when the side effect fails; the post-completion stamp with the documented crash window is the safer trade for a human-in-the-loop product.
- **`test-proposal` seeding route:** not needed — the scripted harness seam exercises the lifecycle honestly end to end.
