## Problem Statement

The PRD describes Shera Bot as a private, general-purpose AI operating environment: three role-specific agents, persistent chats and workspaces, browser and terminal activity, multi-agent delegation, autonomous tasks, provider choice, local-first credentials and memory, approval gates, isolated user containers, recovery, backups, Git worktrees, and an admin console.

That is a coherent platform vision. It is not yet a startup problem statement. The PRD describes what the system can do, but not a narrowly defined person who is currently losing time, money, or opportunity because a specific workflow is broken. It also does not contain evidence that anyone would pay for this product or be upset if it disappeared.

My current diagnosis: **do not build the platform as specified as the first company product**. Treat it as a capability map and validate one painful, repeatable workflow with one persona. The first product should be a wedge that can deliver value without OAuth, three agents, custom providers, multi-tenant containers, autonomous triggers, browser control, backups, or an admin console.

**Position:** the idea is currently a technically ambitious product hypothesis, not a validated startup. Evidence that would change this judgment is three independent users in one segment completing the same workflow repeatedly, at least one paying or making a credible budget commitment, and at least one user reporting that the old workflow is unacceptable after using the prototype.

## Status Quo

The PRD does not document what a target user does today. That is the largest missing section.

Likely status-quo substitutes differ by segment:

- Researchers: ChatGPT/Claude projects, Google Scholar, reference managers, notebooks, browser tabs, scripts, spreadsheets, and manual citation checking.
- Developers: an IDE assistant, terminal, GitHub issues, CI, separate browser tabs, local scripts, and human review of patches.
- Students: general chat assistants, uploaded documents, search engines, note-taking tools, and manual study workflows.

The real competitor is not another multi-agent platform. It is the existing pile of tools plus a user who has learned how to operate it. Shera Bot only wins if it removes a painful coordination cost that the pile creates and does so reliably enough that users change their habit.

The PRD currently assumes that a richer integrated environment is inherently better. That premise is unproven. Users may prefer a single excellent workflow inside tools they already trust over a new environment that asks them to migrate chats, files, credentials, projects, memory, and habits.

## Target User & Narrowest Wedge

The current target is too broad: researchers, developers, and students, with a general-purpose assistant underneath. A solo founder should select one buyer, one recurring job, and one measurable result.

### Recommended wedge: long-running, approval-gated coding tasks for small software teams

Initial persona: a technical founder at a 2–10 person TypeScript SaaS company using GitHub and pnpm who regularly delays small, well-specified fixes because running, validating, and reviewing them interrupts higher-priority work.

Initial job: “Take one failing test, lint error, or typecheck error from issue to reviewable branch during a 15–90 minute unattended window, pause before actions outside the agreed sandbox, and leave a reproducible evidence trail when I return.”

Smallest paid version: a local-only Docker runner for one GitHub repository and one pnpm/TypeScript task. The container mounts only a temporary worktree read/write and a generated task configuration read-only; it does not mount the Docker socket, home directory, SSH directory, cloud credentials, or arbitrary host paths. It runs as a non-root user with dropped Linux capabilities, a process/time/memory limit, and no inbound network. Outbound network is denied except HTTPS to one user-selected model endpoint through a host-side proxy. The user supplies that provider key at runtime; it is never written into the worktree or activity log. The runner may read/write inside the mounted worktree and run Git plus configured pnpm validation commands, then returns a reviewable patch and activity log. Package installation, Git remote writes, deployment, access outside the worktree, and other secret use are disabled in the pilot. One agent is sufficient. A Telegram-like dashboard, browser/research tools, group chat, autonomous schedules, custom provider marketplace, multi-session recovery, and three-agent identity system are not required to test this job.

The pilot has no remote approval dashboard. Because the allowed task surface is pre-approved and external writes are disabled, any action outside the allowlist stops the task and writes a pending-action record. The user reviews that record when they return and starts a new run with an expanded allowlist if desired. “While away” therefore means unattended execution only inside the pre-approved boundary, never indefinite live authorization.

The minimum evidence trail contains the task request, start/end time, commands with exit codes, files changed, diff summary, validation results, approval decisions, failure reason if incomplete, and the exact commit/branch or patch the user can review.

Why this is the best starting hypothesis for a solo founder:

- The pain can be measured in completed tasks, elapsed time, reviewable output, and fewer context switches.
- The buyer has a clearer ability to pay than students and many individual researchers.
- The workflow has a natural trust boundary: code changes and external writes require approval.
- The PRD already contains useful product primitives for this wedge: worktrees, validation, task state, boundary approvals, restart recovery as a future option, and redaction.
- A user can try it on one repository without uploading source code to a new hosted platform or adopting a whole personal operating system.

This is still a hypothesis. If interviews show that researchers have more urgent, repeated pain and will pay, switch the wedge rather than defending the architecture.

## The Six Forcing Questions

### Q1: Demand Reality

Unknown. The PRD supplies no user behavior, payment, or “do not disappear” evidence. Before building the platform, get five interviews and three observed sessions in one segment. Do not count compliments, waitlists, or generic AI enthusiasm.

### Q2: Status Quo

Unknown. Ask each candidate to screen-share the last real task they solved with their current tools. Record every handoff between chat, editor, terminal, browser, Git, and notes. Quantify time, repeated work, blocked steps, and the point at which they abandon or defer the task.

### Q3: Desperate Specificity

Unknown. “Researchers,” “developers,” and “students” are categories, not customers. Name an actual person, their role, the recurring task, and the consequence of leaving it unsolved. For the recommended wedge, that might be a technical founder who loses half a day each week to context recovery and cautious execution of repository changes; it must be a real person, not an invented persona.

### Q4: Narrowest Wedge

The PRD is several products at once. The narrowest credible paid wedge is one repository, one task, one agent, one isolated worktree, bounded tool use, stop-on-boundary behavior, and a reviewable result. If a user will not pay for that, adding group chat and more infrastructure will not fix the problem.

### Q5: Observation & Surprise

Unknown. No observed user sessions are reported. A demo or survey will not answer this. Watch a user work without helping. The important discovery is likely to be what they do instead of using a new agent: copy prompts between tools, avoid risky automation, keep a manual checklist, or abandon tasks that cross too many context boundaries.

### Q6: Future-Fit

Potentially positive, but not yet a thesis. Better models may increase the value of reliable task execution, approvals, recovery, and auditability. They may also make generic multi-agent interfaces commoditized. The durable claim cannot be “AI gets better.” It must be: “As models become capable enough to act, small teams will pay for a trusted execution layer that lets them delegate long-running repository work without surrendering control.” That claim needs user behavior and retention evidence.

## Constraints

- Solo-founder bandwidth is the binding constraint; the current scope spans product, distributed runtime, security, browser automation, model adapters, data infrastructure, and operations.
- Trust and safety are part of the product, not polish. A single credential leak, cross-user isolation failure, or unsafe external action can end the company.
- Model providers, pricing, and tool behavior will change faster than a large platform can be stabilized.
- The PRD says “private prototype,” but many requirements are production-grade: durable replay, backups, restart-safe effects, tenancy isolation, custom providers, recovery semantics, and cross-browser quality.
- No real billing, export, purge, enterprise controls, or public launch are included, so the prototype cannot yet prove willingness to pay or operational viability.
- The product must remain independent from Grok/xAI branding and implementation, as already stated in the PRD.

## Premises

1. **A multi-agent environment is more valuable than a single excellent workflow.** This is currently unproven. The first user test should compare the narrow single-agent task runner against the full conceptual environment.
2. **Users want a new workspace rather than integration into their existing tools.** This is risky. Measure willingness to connect a repository and use a new execution surface before building migration-heavy features.
3. **Researchers, developers, and students share enough pain for one product.** They do not share a buyer, urgency, workflow, or budget by default. Pick one segment until evidence supports expansion.
4. **Local-first isolation is a customer-visible advantage.** It may be a strong trust feature, but only if users understand it and choose it over simpler hosted alternatives.
5. **Autonomy is the primary value.** It may instead be approval-aware reliability, containment, and evidence of what happened. Test the benefit users actually pay for.
6. **The architecture should be built before the wedge is known.** This is backwards for a solo founder. Architecture should follow the first paid workflow, with explicit seams only where the workflow proves them necessary.

## Approaches Considered

### Approach A: Full Shera platform from the PRD

Summary: Build the three-agent, multi-tenant, containerized assistant platform with all prototype acceptance criteria.

Effort: XL

Risk: High

Pros:

- Strong long-term capability map and room for differentiated trust/recovery behavior.
- Exercises the complete runtime architecture early.
- Could support multiple future wedges if the core interaction proves valuable.

Cons:

- No demand proof before a very large build.
- Security, recovery, provider adapters, browser state, and real-time semantics create multiple failure surfaces.
- Makes it hard to learn which feature caused value or failure.
- A solo founder can spend months building infrastructure without discovering a paying user.

Reuses: all sections of the current PRD.

### Approach B: Single-agent coding task runner (recommended)

Summary: Build one bounded local workflow for one repository task: a restricted Docker mount, an isolated worktree, allowlisted commands, validation, stop-on-boundary behavior, and reviewable output. Cross-session resumability is a post-validation option.

Effort: M

Risk: Medium

Pros:

- Clear user, job, result, and willingness-to-pay test.
- Reuses the PRD's strongest primitives without requiring a platform shell.
- Creates a meaningful trust advantage if containment and evidence are excellent.
- Can be tested with five users in weeks rather than a full platform cycle.

Cons:

- Developer tooling is crowded and incumbents are strong.
- Requires careful sandboxing and secret handling from day one.
- May reveal that the strongest value is an integration or service, not a standalone workspace.

Reuses: Git worktrees, validation runner, task state, boundary-stop records, redaction, and provider abstraction where needed. Recovery checkpoints are explicitly deferred.

### Approach C: Research evidence pipeline

Summary: For one research persona, turn a question plus a bounded document/web corpus into an evidence table, citations, unresolved questions, and a report.

Effort: M

Risk: Medium

Pros:

- The Researcher role has a concrete output and quality bar.
- Evidence tables and citations are more specific than a generic chat assistant.
- Can start as a service or concierge workflow before building a platform.

Cons:

- Researchers and students may have low willingness to pay.
- Citation accuracy and source freshness are difficult to guarantee.
- Existing research and chat products make differentiation and distribution difficult.

Reuses: document/PDF parsing, web reading, citations, source indexes, memory, artifact generation.

## Recommended Approach

Choose **Approach B** for validation, while keeping the broader PRD as a non-binding north star.

The first product should not be called a general-purpose assistant in its positioning. Position it around a result: “A local coding task runner that fixes bounded TypeScript validation failures while you are away and returns a reviewable branch with reproducible evidence.” Do not build three agents until users repeatedly ask for delegation across distinct roles or the single agent demonstrably hits a workflow boundary.

The product decision should be reversible. After the first validation cycle, continue only if users complete tasks repeatedly, accept the approval model, and either pay or make a credible budget commitment. Otherwise, pivot the wedge or stop; do not use the existing architecture as a reason to continue.

## Success Criteria

### Validation gate before platform expansion

- 10 conversations with people who recently performed the target workflow.
- 5 observed sessions using their real tools and repository, without a guided demo.
- 3 design partners complete the same task type twice.
- At least 2 users ask to use it again without prompting.
- At least 1 user pays, signs a paid pilot, or commits a specific budget and start date.
- A credible budget commitment means either a non-refundable deposit or a signed pilot agreement naming price, start date, and repository task class; verbal enthusiasm does not count.
- The runner produces a reviewable branch and the defined evidence trail without exposing credentials or accessing files outside the agreed worktree.
- Approval, cancellation, and bounded retry behavior are understood by users and recover safely in test scenarios. Multi-session crash recovery is deferred unless interviews identify it as paid pain.

### Product signal that supports expansion

- Users describe the value in their own words as delegation/reliability/trust, not “a cool AI workspace.”
- Users return for the same job at least weekly.
- Retention persists even when model quality improves or changes provider.
- Users request additional roles or agents because the current workflow has a proven boundary, not because the platform menu suggests it.

### Continue, pivot, or stop rubric

- **Continue:** at least 3 design partners each run 2 qualifying tasks, at least 2 ask to reuse it, and at least 1 pays the pilot price.
- **Extend the test once:** exactly 2 design partners complete a second task and at least 1 signs the paid pilot; recruit 5 more candidates without expanding product scope, then apply the rubric again.
- **Pivot the wedge:** observed pain is real but users consistently want a different recurring task, deployment mode, or buyer; preserve only primitives required by that newly observed job.
- **Stop:** fewer than 3 of 10 interviewees performed a comparable workflow in the last month, fewer than 2 complete a second task, nobody accepts a concrete paid pilot, or users refuse the local trust/onboarding model.
- **Stop for feasibility:** the constrained runner cannot prevent access outside the worktree, produces unreproducible changes, or total model/tool cost for a company's pilot exceeds 20% of that company's US$250 pilot revenue before human support time.

## Distribution Plan

Start with founder-led distribution. Recruit technical founders at 2–10 person TypeScript SaaS companies through direct outreach, local developer communities, and personal network referrals. Ask for a real failing test, lint error, or typecheck error, not a product demo.

The first offer is a four-week, founder-supported pilot at **US$250 per company**, covering up to 10 bounded tasks on one repository. The price is a demand probe, not final packaging. Track model/tool cost per task and keep it below 20% of collected revenue; track human support separately because a pilot that requires constant founder intervention has not validated software economics.

Users receive the pilot as a versioned local Docker image plus a small configuration file for one GitHub repository and the allowed pnpm commands. The founder onboards each company live, supplies updates manually, and maintains a signed checksum and changelog for every pilot release. No public package, auto-update system, cloud dashboard, or GitHub App is required for the first five users. If the pilot validates, publish the runner through GitHub Container Registry and add CI that builds, tests, scans, signs, and publishes versioned images from tagged releases.

Do not launch open signup, student pricing, a broad provider marketplace, or a public multi-agent platform before the first wedge has repeat usage. The initial distribution advantage must come from learning faster than larger competitors, not from trying to out-feature them.

## Dependencies

- A real design partner and access to a non-sensitive or safely redacted repository.
- A clear threat model and sandbox boundary before handling credentials or external writes.
- A minimal local execution runtime with single-task state and a worktree; durable cross-session orchestration is deferred.
- A host-side HTTPS model proxy that injects a runtime-only BYOK credential, restricts the destination to the configured provider, meters usage, and redacts request/response metadata stored in the activity log.
- A reliable validation runner for the target language/build system.
- A way to capture task evidence without exposing secrets.
- A pricing and pilot agreement that tests payment rather than compliments.
