## Decision and rationale

**The zero-side-effect architecture: the preview is a READ model with a byte-level proof, and the confirm is the only writer.** The gate's whole safety argument is that opening it, editing the roster in it, and closing it cannot touch anything (D30: nothing executes before confirmation). This is enforced at three layers, each independently proven:

1. **GET-only until confirm.** The two preview routes (`GET /v1/operation-definitions`, `GET /v1/operation-definitions/:id/preview`) are pure reads over the in-memory pack catalog and the agents repository's read-only `getAgent`; the preview builder writes nothing — no rows, no receipts, no journal appends, no events. The browser proxy allowlist (`runtime-access.ts`) admitted only the GETs in chunks 1–2; chunk 3 adds exactly one POST (`/v1/operations/launch`) and nothing else, so the wire shape itself cannot express "execute from the preview".
2. **The fingerprint probe.** The sqlite adapter (the only module allowed SQL, D23 rule 2) exposes `sqliteSideEffectProbe`: a second, strictly read-only connection that computes row counts AND a whole-database content fingerprint (every user table). The automated proof composes the real runtime over real SQLite and asserts the database is byte-identical across definitions reads, preview reads with roster/coordinator overrides, and the typed 404/400 paths — and names the proof points (D30): zero operation rows, zero task-run rows, zero Operation-chat rows, zero conversations. Chunk 3 extends the same proof through the confirm lens: modal open (reads) + close leaves the fingerprint identical (cancel has no request to make — the close is a pure client state change), and the launch creates exactly one of each and no more.
3. **Re-validation at launch — the preview's edits are never trusted (D36).** `launchOperation` re-resolves the definition from the pinned pack at the moment of confirm (an unknown id is the typed `OPERATION_DEFINITION_NOT_FOUND`) and hands the confirmed roster/coordinator to the SAME `createOperation` machinery the ad-hoc flow uses — pack-membership re-validation, the D36 refusal vocabulary (`OPERATION_ROSTER_REFUSED` 403 for an out-of-pack candidate, `OPERATION_COORDINATOR_NOT_FOUND` for an out-of-pack coordinator), and the D29 pinning snapshot are the shared code path, not a fork. The web client posts the envelope built FROM THE PREVIEW AS DISPLAYED (the effective overrides the user saw), so what the runtime re-validates is exactly what was on screen; the runtime, never the browser, decides what is created.

**The confirm creates EXACTLY ONE Operation chat and ONE first run (D30/AC23).** `launchOperation` composes three shared units — `createOperation` (definition_ref + pinning snapshot, named from the definition's title: the launch is the first flow that sends a `definition_ref` with a derived name, closing the S14 deferral note), `createRun` (D8 CREATED, D26 cursor 0 — typed creation, D34), and the journaled chat binding `getOrCreateChat` (D41) — and answers `{operation_id, run_id, chat_conversation_id}` (201; a replay answers the same ids with 200). The response carries ONLY ids; the chat page reads the full detail from the operation read model after navigation (the S14 read-after-write pattern). The web mutation invalidates `["operations", workspace]` on success and the launcher navigates to the new chat — the S14 create pattern.

**Route-namespace choice: the launch rides `/v1/operations/launch`, NOT a sub-path of the capture.** The S13 route table owns `GET /v1/operations/:operation_id` — a literal "definitions"/"launch" GET sub-path would be captured by that parameter (Express matches in registration order), which is why the preview read model got its own `/v1/operation-definitions` prefix in chunk 1. The launch is a POST, so the GET capture cannot swallow the literal "launch"; the path stays under `/v1/operations/` (the Operation command namespace) and is distinct from every S13 mutation route (which all require the `:operation_id` segment). The same distinct-path discipline is documented in the route constants and the test headers so the choice survives review.

**Idempotent launch receipts (D23 rule 6).** The launch is idempotent on `(workspace_id, idempotency_key)` with command type `operation.launch`: the receipt lookup answers a replay with the ORIGINAL `{operation_id, run_id, chat_conversation_id}` (result shape re-validated typed — corruption, never a fallback), so a retried confirmation can never duplicate an Operation; a key already spent on a DIFFERENT command family (e.g. a message send) is the typed conflict (`OPERATION_COMMAND_INVALID`, conflict category) — the same discipline as the message send. A different key is a different launch decision (a second Operation). Recorded bounded limitation: the receipt is written AFTER the three creations commit (the launch composes three shared transaction units rather than forking a fourth monolith), so a crash in the window between the chat creation and the receipt write could leave an Operation whose replay re-launches a sibling; the runtime gateway's journaled launch supersedes this seam when the authoritative execution flow lands. The envelope is the contracts `OperationLaunchCommand` (D16-command shape: `idempotency_key`, `actor`, `issued_at`; no `command_id`/`expected_version` — the launch is not a run-state transition), registered in the contract registry with round-trip and unknown-field fixtures, and the OpenAPI clients were regenerated (`pnpm gen:clients`).

**The credits formula and the approval ladder are DOCUMENTED PLACEHOLDERS with recorded deferrals.** Credits (D20): min = 1 credit per platform-provider Agent, max = 5, rendered as a bounded range (`3–15 Shera credits` for the three-Agent research-paper roster; the override recomputes live) with the settlement note verbatim (the runtime reserves before execution, settles against actual usage, releases unused reservations; the preview consumes nothing); Agents on custom providers consume no Shera credits. Real pricing is the providers slice's (S23) — the formula note says so on the surface. Approval classes (D35): the pinned pack references tools without risk classes (the runtime owns tool definitions, D38), so the preview applies the documented default ladder to tool ids — read-only → auto_execute; local-mutation / code-execution / repository-mutation / external-write / destructive-irreversible → approval_required — and the mapping note states the runtime re-derives every class at execution time. The ladder is live: adding the Developer (tool_code_exec) to a preview re-renders the code-execution class with "pauses for your approval". The approval-ARTIFACT gate remains S20's; the classes are named without promising outcomes (regex-audited at the backend and mirrored over the web render).

**The honest-null expected-outputs posture (G4).** No manifest definition declares an outputs field, so the preview derives the statement from the definition's purpose with an explicit `source: "purpose_derived"` and the reason verbatim ("The pinned pack's definition carries no expected outputs field."); a definition with no derivable outputs renders the whole group null and the UI shows "The pack does not declare expected outputs for this Operation." The UI never invents artifacts, and the connectors group cannot even express a connected connector (`connected: z.literal(false)` — G2): the surface renders "Not configured" and the word "Connected" never appears.

## Alternatives considered (preserved)

- **`GET /v1/operations/definitions` / a `:operation_id`-free sub-path under the S13 namespace:** rejected — the S13 parameter route captures literal segments in registration order; the distinct `/v1/operation-definitions` prefix and the POST-only `/v1/operations/launch` keep every route unambiguous without reordering S13 registrations (a reordering would be a silent behavior change to shipped routes).
- **Trusting the preview payload at launch** (persisting the previewed values without re-checking): rejected — the preview is a read model computed minutes earlier from query params; between preview and confirm the pack could have been upgraded. D36 makes the runtime's re-validation the point of the gate; the launch path reuses `createOperation` precisely so the re-validation cannot drift from the ad-hoc flow's.
- **One mega-transaction for operation + run + chat + receipt:** rejected for this slice — it would fork the creation machinery (duplicating roster validation, pinning, and the journaled binding) to buy atomicity across units that are each individually atomic; the recorded crash-window limitation is the honest trade, and the runtime gateway's journaled launch supersedes it.
- **A separate preview/confirm web state store (e.g. persisting the user's edits client-side and posting them):** rejected — the server recomputes every group on every edit (the override refetch), so the posted envelope is derived from the LAST SETTLED read model; a client-side edit store would let the wire diverge from what the user saw.
- **Launching from the menu directly (skip the gate):** rejected by D30 itself — templates launch into the preview, never straight to a chat; the launcher's own copy states the promise ("Nothing runs until you confirm").
- **Rendering the confirm button inert until "chunk 3" (the chunk-2 marker):** superseded by this chunk — the `data-testid="launch-inert"` marker and its title are gone, replaced by the live control; the suite asserts the marker's ABSENCE so the temporary contract cannot silently return.

## Recorded follow-ups (not blocking)

- **Receipt-last crash window:** a crash between the chat creation and the `operation.launch` receipt write can make a replay launch a sibling Operation; the runtime gateway's journaled launch supersedes this seam (recorded limitation above, not a silent gap).
- **Launch-envelope `issued_at` freshness:** the runtime accepts a stale `issued_at` (the prototype has no replay-window policy); a bounded-clock check arrives with the gateway's command policy.
- **Coordinator "none" at launch:** the gate allows confirming peer-to-peer (D49); whether a pack-defined launch should WARN when the confirmed coordinator is "none" while the definition names one is a product question for the owner — the current surface shows the radio state honestly and persists exactly what was confirmed.
- **Definitions-list caching:** the menu refetches per mount (`staleTime: 0`); a pack upgrade mid-session is therefore always reflected, at the cost of a GET per navigation — revisit with the read-model caching slice if it matters.
