## Decision and rationale

**The trigger record is the ONLY origin of an autonomous run (G2), and the ledger is the ONLY thing that fires.** Migration v19 adds the two STRICT, workspace-scoped tables — `trigger_records` and `trigger_firings` with the idempotency-key uniqueness the dedup guarantee rides (D23 rule 6: the key is data — `${kind}:${trigger_id}:${delivery-or-occurrence-key}`) — behind a closed seven-kind vocabulary (schedule, file_watch, git_watch, webhook, task_completion, condition, external_event) enforced at the storage layer. Every run a trigger creates carries its origin as a typed contracts event (`trigger.scheduled`, `trigger.webhook`, `trigger.file_event`, `trigger.git_event`, `trigger.task_completed`, `trigger.condition_met`, `trigger.external_event`), never prose; the typed create refuses a prose-only body at the HTTP schema, the service, and the per-kind configuration schema (G2 pinned three ways, plus a permanent boundary-guard test — see below).

**The fire pipeline is claim → reserve → gate → run → walk → settle, each step recorded (at-least-once, never twice).** A due occurrence is claimed ONCE through the ledger's idempotency key (a duplicate occurrence is the typed `deduplicated` outcome and creates NO second run); the credit-reservation seam is consulted before anything runs — a refusal pauses the trigger with the D48 `insufficient_credits` reason, journals the decision on the trigger's own event stream, and creates NO run (the resume-after-top-up path fires the next occurrence through the same route family); the D17 provider gate is consulted before the run exists (an unconfigured trigger's refusal is recorded as a failed firing with the typed code); the run walks the autonomous plan runner and settles with the run linkage written back to the ledger. At-least-once recovery is the boot reconciliation: claimed firings whose run never landed (the crash-between-claim-and-run window) are re-driven, and missed occurrences are decided per trigger by the catch-up-versus-skip policy with the decision RECORDED per occurrence — the fake-clock pins cover skip recorded, catch-up once each recorded, and the bounded remainder recorded as skipped.

**The scheduler owns occurrence math over the adopted cron-parser; the web never imports a cron library.** The schedule clock wraps cron-parser (MIT, exact-pinned 5.10.2) with typed refusals, next-occurrence strictly AFTER the reference instant in UTC, half-open (from, to] missed-occurrence enumeration, and a bounded catch-up replay (`CATCH_UP_MAX_OCCURRENCES = 50`) whose remainder is recorded as skipped — a long-down runtime replays a bounded, visible decision, never a silent flood. The runtime-owned clock is an injected seam (`schedule(delayMs, fn)` returning a cancel handle; the default an unref'd interval timer), so tests drive the clock and the tick loop is a production convenience, never the truth source — the truth is the ledger and the bookkeeping columns.

**Watchers are signature-gated: one firing per REAL change, never per intermediate write.** chokidar 6.0.0 (MIT, exact-pinned) is the LIVE detection source; the DECISION is a content signature compared against the trigger's stored signature — workspace files sign as row + content hash, agent private folders as a bounded stat walk of the FileAgentFolderStore layout, git watchers as the watched branch's sha, conditions as typed-predicate edge state. A rapid-write flood coalesces into ONE firing carrying the net signature (the once-per-real-change pin); a restart re-signs before arming so the same content never re-fires (AC4, for watchers and schedules both); a changed-then-reverted file genuinely did not change. The completion cascade subscribes to run settlement: a task_completion trigger fires a follow-up run with `parent_task_id` linkage when a watched run settles inside the configured outcome vocabulary (AC6), and condition triggers evaluate typed predicates (false→true edges, artifact counts against real artifacts).

**Webhooks: the receiver is a plain Express route with a digest-compared secret and a content-free summary (G3).** The optional shared secret is digest-compared in constant time (the plaintext exists only in the request frame); the dedup key is the delivery-id header or the body digest; the delivery body NEVER enters the journal, the ledger, or a log — only the bounded derived summary (`<content-type> <N>b delivery`) — and a duplicate delivery answers 200 `deduplicated` with exactly one run (the delivered-twice AC). The receiver is deliberately OFF the browser allowlist: deliveries come from external senders to the runtime's loopback surface, never through the browser proxy (pinned by the proxies suite's refusal leg).

**One autonomous task completes end to end with zero user input (the AC12 proof).** The composed proof test drives a real scheduled firing through the full pipeline into the autonomous plan runner: the model-call leg through the provider seam (a bounded typed plan — prompt inside a bounded vocabulary, optional typed tool step, optional artifact spec), the tool-use leg through the S21 executor (the ONE execution path, the canonicalArgsDigest tie, and the D35 ladder held for autonomous work: a gated tool pauses the run for the user's decision, never auto-approved — G6), and the artifact leg through the S17 artifacts repository (provenance-stamped, content non-empty). Without a declared provider the walk is the honest no-legs walk whose bookkeeping still settles truthfully — the runtime never fabricates model output (G4).

**The UI is the truthful schedules & watchers settings surface.** Every card renders the scheduler's OWN record — state, pause reason (the D48 credit pause with its unblocking path verbatim), last firing ("never fired yet" when absent), next occurrence ("— (event-driven)" for the event-driven kinds), and recent firings as run cards naming their trigger ("from schedule: weekly literature sweep") — with the capture harness's AC9 truth leg FAILING the build unless the rendered text matches `runtime.schedules.getTriggerView`'s record (en-GB, UTC). Pause/resume/edit are the AC10 controls (the edit is inline, never a modal; a schedule's next occurrence recomputes from the edited expression). The browser trust boundary grows by exactly the schedules reads (GET list + GET firings) and the four mutation POSTs with the acting actor bound SERVER-SIDE from the session — including create (below) — and NO webhook path. The missed-occurrence policy renders in the product's own words ("missed runs are caught up / skipped"), never a raw enum (the taste pass).

**The create posture: the creating actor is the session identity, server-side.** The runtime's create contract requires an actor (created_by is an audit field); the browser client deliberately sends NO actor on create, and the proxy's session-actor binding supplies it — the S20/S23 convention extended to creation, pinned by two proxy legs (a body-asserted actor is overwritten; an actor-less body still arrives with the session identity). Pause/resume/edit keep the placeholder-then-overwrite shape. A client-chosen created_by never reaches the runtime through the browser.

## Alternatives considered (preserved)

- **BullMQ repeatable jobs + Redis SET NX EX idempotency (the issue's open-source leverage note):** REJECTED per E27's recorded scope correction — no Redis dependency in the prototype; the runtime owns scheduling (D11) over SQLite, and the ledger's idempotency-key uniqueness gives the exactly-one-run guarantee without a second datastore. The leverage note's OTHER prescriptions WERE adopted as written: chokidar for file watchers and a plain Express route for the webhook receiver.
- **Replaying every missed occurrence unbounded:** rejected — an unbounded catch-up over a long-down runtime is a silent flood and hides the decision; the bounded replay (50) with the remainder RECORDED as skipped keeps each occurrence's fate visible per E5.
- **Recomputing schedule math in the UI:** rejected — AC9's truth source is the scheduler; a permanent boundary-guard test refuses any cron library import in web code (`no web component or lib imports a cron library — the scheduler owns occurrence math`), so the UI renders the runtime's record or nothing (G4).
- **A browser-proxied webhook receiver:** rejected — a webhook delivery is an EXTERNAL event, not a browser action; proxying it through the session would bind an identity it does not have and widen the browser surface for no honest need. The receiver stays runtime-loopback-only.
- **Extending the OperationRun contract with a `created_from` field so the Operation-runs panel names triggers:** deferred — AC10's run-card naming is satisfied on the settings surface where trigger runs live (RunCard renders "from {kind}: {name}", tested in schedules-ui); the runs panel has no trigger field on the wire and no consumer need was demonstrated, so the contract is NOT extended this slice (the recorded reading; a later extension is additive).
- **An LLM-evaluated condition family:** the condition trigger kind exists and fires on TYPED predicates (edges, artifact counts) in this slice; an agent-evaluated (LLM) condition is future work behind the same trigger record — the predicate vocabulary stays typed and bounded until then.
