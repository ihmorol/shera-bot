## Decision and rationale

**The D46 sub-item at S13 (issue #14's ninth criterion — the record E19 promised): subordinate execution = a typed child run through the runtime.** E19 (S10) resolved the D46 sub-item at the engineering level with the same-identity worker reading and explicitly deferred the "another same-Pack Agent as subordinate" reading (reading 2) to S13's collaboration contracts. This is that record. S13 implements subordinate execution as **EXACTLY ONE child run per TaskDelegated D7 event** with `parent_task_id` = the delegating run's id (D34/D46):

- the child run is created ONLY through the runtime's delegation path (`applyDelegation`); the plain `appendCollaborationEvent` refuses `type === "TaskDelegated"` with the typed `OPERATION_EVENT_INVALID` (added in the review round as defense in depth — the HTTP route already routed the type to the delegation path, and the guard closes the in-process bypass that could persist the event without its child run);
- the event append, the child run, and the idempotency receipt commit in ONE transaction (D23 rule 6); a replay answers the ORIGINAL child run; a child's failure never touches the parent run;
- child runs carry **no agent identity of their own** — sender attribution stays with the delegating Agent's event, and the child is executed through the workspace's harness seam exactly as E19 recorded.

**Reading 2 (one Agent delegating to a DIFFERENT rostered Agent as its subordinate with delegated identity) STAYS DEFERRED.** Nothing in the v6 schema prevents it — roster membership plus the D42 coordinator model carry both readings (E19's neutrality argument stands) — but this slice ships and tests the identity-less child run, and the choice is recorded here rather than silently made in code. Concurrency limits remain the S16 admission-control placeholder; E19's one-run-per-(workspace, Agent) baseline is inherited unworsened. A product-level reversal supersedes this record via a recorded decision (PRD §24), never a silent edit.

**D36 cost posture: risk classification is CLIENT-asserted today — a bounded limitation, not a silent gap.** The contracts envelope carries `RosterRiskClassification` (same_pack / cost_or_access_increasing / requires_approval); the UI's explicit confirm step arms every add (the conservative superset of the D36 approval requirement); and the runtime validates what it CAN: pack membership against the PINNED catalog at both the contract boundary and the service's catalog re-check (`agent-not-in-pack`, `foreign-pack-refused`), plus the envelope's internal consistency (a cost-increasing add without the flag is refused `cost-increase-needs-approval` and the refusal is PERSISTED). The runtime has NO per-Agent cost model, so `requires_approval` derivation is client-asserted; **server-side derivation is deferred to the providers slice, when per-Agent cost metadata exists to derive it from.** The declared flag itself IS this slice's contract: an approval-declared cost-increasing add applies and the membership row records `requires_approval = 1`, exposed on the detail read model (tested at both the service and HTTP seams).

**The approval-ARTIFACT gate is the approvals slice's (S20).** This slice records the flag; the gate that demands an approval artifact before APPLYING a flagged change arrives with S20 — until then a flagged add proceeds, which the confirm step makes explicit. Transition legality is deferred the same way: `applyRunState` validates the D8 vocabulary (no second state machine, AC24) — WHICH state may follow which is the runtime gateway's job, and no HTTP route exposes run-state writes in this slice (the AC8 test drives the terminal state through the in-process service seam for exactly that reason).

**Storage: the v6/v7 migration shapes.** v6 (`operation-chat-records`) creates `operations` (the D31 record with the pinning snapshot normalized: pack identity, capabilities JSON, provider snapshot on the row — the roster is NOT in the JSON), `operation_roster` (the membership single source of truth with `requires_approval`, composite key `(workspace_id, operation_id, agent_id)`), `operation_roster_refusals` (append-only D36 evidence with the raw `command_json`), `operation_coordinator_events` (D49 lifecycle, unique on `(workspace_id, event_id)`), `operation_runs` (D8 state CHECK, D26 cursor, credits/artifacts JSON, `parent_task_id` — no FOREIGN KEY by design, the writer validates), and `operation_collaboration_events`. v7 (`operation-chat-binding-and-addressing`) creates `operation_chats` (one conversation per workspace+operation, PK `(workspace_id, operation_id)`) and `operation_message_recipients`. Every product table carries `workspace_id` (E12, enforced structurally and by the boundary contract test). Reads parse back through the contracts schemas — a stored shape that no longer conforms is the typed `OperationRecordCorruptError`, never silently returned JSON.

**Stream design: run-scoped streams + the `operation:<id>` chat-stream sentinel.** Collaboration events key on `(workspace_id, stream_id, sequence)`; the stream is the RUN when `run_id` is set and the Operation chat itself (`operation:<operation_id>`, a prefix no run id may take) when null. Sequences are 1-based and gapless per stream, allocated inside the same transaction as the insert (BEGIN IMMEDIATE serializes writers; the composite PK is the loud backstop); a run-scoped append advances that run's `events_seq_cursor` in the SAME transaction; a duplicate `(workspace_id, event_id)` is the idempotent no-op returning the ORIGINAL event (AC3).

**Addressing storage (D7 recipient semantics).** `@`-mentions resolve against the Operation roster at SEND time; the resolved recipient Agent ids persist in `operation_message_recipients` written in the SAME transaction as the message append; an unaddressed message stores no row (the read model reports `[]` = Operation-wide); an unresolvable mention resolves to nothing — the literal text is never rewritten and the send never fails on it.

**Receipts (D23 rule 6) — including the new remove-roster receipts.** Three command families replay through the receipts seam: delegation (`operation-task-delegated:<event_id>`), the message send (the envelope's idempotency key, `operation.message_send`), and NOW the remove-roster command (`operation-remove-roster-agent:<command_id>`, workspace-scoped — added in the review round): inside the transaction, a receipt hit returns the original applied outcome re-read from the CURRENT record (command type and result shape validated typed — corruption, never a fallback); on a miss, an absent member is the idempotent no-op — the add/remove symmetry with the add's `ON CONFLICT DO NOTHING` — returning the current record instead of 404ing a replayed remove, and a real removal writes its receipt in the same transaction as the DELETE (the no-op writes none: it has no effect to record and re-derives the same answer). Recorded consequence: no service path produces `OPERATION_ROSTER_AGENT_NOT_FOUND` anymore; the transport's typed-error mapping keeps the code as defense-in-depth. The add stays receipt-free (naturally idempotent).

**Reads.** The merged thread (D41) interleaves the chat conversation's durable messages with every D7 collaboration event as typed, attributable items; the thread read re-validates the journaled sender through the `MessageSender` union (added in the review round — a drifted row is typed corruption, never a cast item). The refusals read is capped at the **20 most recent, newest first** (`ORDER BY id DESC LIMIT 20`): the append-only evidence table is never read back in full, "recent" is honest, and the web detail's `recent_refusals[0]` pick becomes the actually-most-recent refusal (it previously surfaced the oldest).

## Alternatives considered (preserved)

- **Keeping the 404 for a replayed/absent-member remove** (the status quo the review rejected): rejected — it answered a committed removal's replay with a state error, breaking the receipts discipline applyDelegation and the message send already hold; idempotent commands answer idempotently.
- **Writing a receipt for the absent-member no-op too:** rejected — the no-op has no effect to record and is naturally replayable; receipts record effects, and the red test pins exactly one receipt row for the double-apply case.
- **Server-side `requires_approval` derivation now:** rejected — no per-Agent cost model exists; deriving would fabricate authority the runtime does not have. Deferred with the metadata to the providers slice (recorded limitation, not silence).
- **D46 reading 2 (delegated identity) now:** rejected — E19's rationale stands; the shipped, tested shape is the identity-less child run, and reading 2 needs delegated-identity semantics no slice has specified yet.
- **An uncapped refusals read:** rejected — an append-only table read in full grows without bound and made "recent" a lie; the 20-row window matches the detail read model's consumption.
- **Seeding the sender-corruption test with raw SQL:** rejected by the AC7 boundary guard itself — the corrupt journal row is constructed through the `EventJournalRepository.append` seam (schema-agnostic storage; validation is the read model's job), keeping SQL inside the adapter.
